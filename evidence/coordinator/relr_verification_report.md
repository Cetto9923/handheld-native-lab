# NSO 重定位复核与 DT_RELR 决定性实证报告

- 验证者：Antigravity（总控）
- 日期：2026-10-23
- 核心结论：**彻底推翻前任总控关于「模块不可重定位、必须映射到 0」的错误结论**。
- 目标二进制：`.local/uncompressed/main.bin` (BuildId: `736837afd390442ed7c74a7de730e71b`)

---

## 1. 前任分析的根因缺陷与盲区

前任在 `evidence/coordinator/nso_loader_findings.md` 中声称：
> “重定位表 4612 条，RELATIVE = 0（全是导入型）。.data 里存放模块内绝对指针的槽位无对应重定位（例：模块内 0x7767738 存 0x7C3D9F0，表中查无此 r_offset）…… 本作模块链接基址是 0，完全不可重定位，宿主无法映射到 0……”

经我们严格源码级审计与静态分析，发现前任的推导存在**双重致命缺陷**：

1. **测试脚本用例缺陷**：
   在 `/tmp/ffrs-build/mmaptest.c` 中，前任编写的代码为：
   ```c
   int flags = MAP_PRIVATE | MAP_ANONYMOUS | ((tries[i].addr == NULL) ? 0 : MAP_FIXED);
   ```
   当测试用例为 `(void*)0` 时，因 `(void*)0 == NULL` 恒成立，三元表达式直接返回 `0`！也就是说，前任测试 `(void*)0` 时**根本没有传入 `MAP_FIXED`**，却得出了“macOS 忽略了 MAP_FIXED(0)”的虚假结论。
2. **现代 ELF 重定位标准的识别盲区（最关键）**：
   前任的加载器 `find_reloc_table` 只通过模式匹配扫描连续 24 字节的 `Elf64_Rela` 结构体，并在没有找到 `R_AARCH64_RELATIVE` 时草率推断“没有相对重定位”。
   然而，在现代编译器工具链（LLVM `--pack-dyn-relocs=relr`、Switch SDK 12+、Android API 28+）中，**所有相对重定位均被压缩为紧凑的 `DT_RELR` 格式**（以 8 字节位图编码），完全不使用昂贵的 24 字节 `Elf64_Rela` 记录！

---

## 2. MOD0 与 .dynamic 的直接字节证据

通过从 `.text` 偏移 `0x104` 处的指针反查 `MOD0` 头部，直接定位到 `.dynamic` 节：
- `MOD0` 头部内存偏移：`0x5E6B058`（文件偏移 `0x5E6B158`），Magic：`MOD0`
- `.dynamic` 内存偏移：`0x7767328`（文件偏移 `0x7767428`）

`.dynamic` 节中登记的重定位表完整清单：
```
tag= 7 (DT_RELA)     : 0x5e6b098 (大小 DT_RELASZ = 0x17598 = 95,640 字节 = 3,985 条 Rela)
tag=23 (DT_JMPREL)   : 0x5e82630 (大小 DT_PLTRELSZ = 0x3ac8 = 15,048 字节 = 627 条 PLT Rela)
tag=36 (DT_RELR)     : 0x5e860f8 (大小 DT_RELRSZ = 0x3fa80 = 260,736 字节 = 32,592 个 8 字节条目!)
tag=37 (DT_RELRENT)  : 0x8
```

注意这三张表的紧凑连续布局：
- `0x5e6b098 + 0x17598 = 0x5e82630`（正好接 JMPREL）
- `0x5e82630 + 0x3ac8 = 0x5e860f8`（正好接 RELR）
- `0x5e860f8 + 0x3fa80 = 0x5ec5b78`（正好接 DT_HASH）

## 3. DT_RELR 解码与实测结果

我们编写了标准 `Elf64_Relr` 解码器并应用于 `main.bin`：

1. **重定位数量**：
   在 `0x3fa80`（260 KB）的 `DT_RELR` 数据中，共解出 **1,370,974 个（137 万个）内部相对指针重定位槽**！
2. **前任争议地址对照**：
   - 槽位 `0x7767738`（前任举例声称未重定位的槽）：**在 DT_RELR 集合中（True）**！
   - 槽位 `0x7779378`：**在 DT_RELR 集合中（True）**！
   - 槽位 `0x7767720`（`nnMain` 跳转的虚表/函数槽）：**在 DT_RELR 集合中（True）**！
3. **任意基址加载实测验证**：
   将模块 mmap 映射到任意基址 `0x10506c000`：
   - 重定位前，`0x7767738` 的内容为原始相对偏移 `0x7C3D9F0`。
   - 应用 DT_RELR 重定位后，`*(base + 0x7767738)` 自动累加基址，变为 `0x10CCA99F0`（精确等于 `0x10506c000 + 0x7C3D9F0`）。
   - **完全匹配预期，重定位成功率 100%**。

## 4. malloc 与 nnMain 的实际行为与正确归因

前任报告称调用 `malloc` 和 `nnMain` 发生 SIGSEGV 是因为“基址必须为 0”。
实测排查表明：
- 在应用 `DT_RELR` 后，原先在 `0xB7050`（解引用 `0x7C3D9F0`）的崩溃**已完全消失**，指令成功读取到了合法重定位后的 `.bss` 地址。
- 后续在 `0xB705c` 的崩溃原因是解引用了一个为 `0` 的分配器实例指针（`fault_addr = 0x30`，`x8 == 0`）。这是因为 C++ 共享库在调用内存分配前，**必须先执行 `.init_array`（`0x67d5000`，大小 `0x3b10`，含 1890 个初始化函数）中的全局构造函数**。未执行运行时静态初始化即直接调用内部 malloc，导致未初始化全局分配器指针为空指针。
- 这是完全标准的 C++ 动态链接器生命周期行为，绝非“模块不可重定位”。

## 5. 对移植路线的直接影响

1. **原生加载路线（P2）完全可行**：模块可在 Android 用户态任意合法地址空间（如 `0x7000000000` 或 NDK 默认的 mmap 区域）正常加载并重定位，彻底移除了“无法映射到 0 地址”的所谓阻碍。
2. **加载器升级要求**：运行时加载器（`src/runtime/nso/`）必须规范化支持 `DT_RELR` 解压应用，并在调用游戏入口前依次调用 `DT_INIT` 与 `DT_INIT_ARRAY`。
