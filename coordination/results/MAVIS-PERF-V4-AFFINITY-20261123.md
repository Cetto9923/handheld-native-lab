# 第 5 轮：把渲染线程钉在超大核（实机 +38% 帧率）

## 1. 本轮目标

上一轮（第 3/4 轮）把 texel 方向连续证伪两次后（L-029 止损），剩下的唯一大杠杆是
**CPU 调度层**：掉速时所有子域等比放大 1.75x，是"CPU 整体变慢"的特征。本轮要回答：

1. 帧率掉速的**真因**是什么（排除热降频、排除抢占）？
2. 能不能在**不改变任何特效与显示**的前提下把它修好？
3. 修好后兵工厂深处能不能稳住 **40 Hz 以上**？

## 2. 定位过程：先钉"谁在干活"，再看"跑在哪"

### 2.1 线程级归属（决定性）

用 /proc/<pid>/task/<tid>/stat 的第 39 字段（最后执行核）和第 14/15 字段（utime+stime）
逐线程采样（10 秒窗口，jiffies 增量）：

| 线程 | jiffies/10s | 占比 |
|---|---|---|
| `dm-gfx`（图形翻译线程） | **+811 ~ +918** | **约 90~100% 单核** |
| `ffrs.gamewindow`（主线程） | +43 ~ +50 | 约 5% |
| `ffrs-guest` x 2 | +0（恒定 33 / 15） | 约 0% |

=> 进程内几乎所有工作都在 `dm-gfx` 一个线程上。**帧率 = 1000 / dm-gfx 的每帧 CPU 时间**。
（L-067 当时写的是"游戏主线程在 cpu3~6 迁移"，主线程其实只有 5%——**该归因在第 6 节显式撤回**。）

### 2.2 核拓扑（实测，不是推测）

/sys/devices/system/cpu/cpuN/cpufreq/cpuinfo_max_freq：

| CPU | 档位 | max | 常态 cur |
|---|---|---|---|
| cpu0~2 | Cortex-A520 | 2.016 GHz | 1.709 GHz |
| cpu3~6 | Cortex-A720 | 2.803 GHz | 2.707 GHz |
| **cpu7** | **Cortex-X4（超大核）** | **3.014 GHz** | 0.63~3.01 GHz |

### 2.3 核掩码：真正的根因

逐线程读 Cpus_allowed_list（/proc/<pid>/task/<tid>/status）：

```
dm-gfx                = 0-6      <- 只有它被排除超大核
ffrs.gamewindow       = 0-7
ffrs-guest            = 0-7
RenderThread / GameThread / hwuiTask0 / SurfaceSyncGrou / ...（共 40+ 线程）= 0-7
```

**全应用 40+ 个线程里，只有 `dm-gfx` 一个被限制成 0-6**，也就是**被排除在 Cortex-X4 之外**。
这解释了"所有子域等比变慢"：翻译线程被挪到了 IPC 明显更低的 A720 核上，
1.6x 的每帧 CPU 时间正好对应 X4 与 A720 的 IPC+频率差距。

### 2.4 收窄的时刻

用引擎自己的窗口仪表记录每次的掩码（`NVN AB aff ... mask=0x..`）：

- 会话 A：present 61 时 mask=0xff -> present 2341 时 mask=0x7f
- 会话 B：present 61 时 mask=0xff -> present 4681 时 mask=0x7f

外部采样也正好卡住翻转点（同一会话、同一场景 draws=602）：

| 时刻 | mask | dm-gfx 所在核 | fps | submit_cpu_ms |
|---|---|---|---|---|
| 进入深处 | 0-7 | **cpu7** | **45.86** | **15.42** |
| 约 12 s 后 | 0-6 | cpu6 | **33.58** | **24.85** |

**同一份工作量（draws=602、ops/draws 不变），仅因为线程所在核不同，每帧 CPU 时间差 1.6x。**
这也终于解释了上一轮记下的怪现象："进入位置后约 20 秒帧率从 40+ 掉到 26~30 并保持"——
掉速的**时刻**就是掩码被收窄的时刻。

### 2.5 谁收窄的

排查过并**排除**：

- 本仓源码：无任何 sched_setaffinity / pthread_setaffinity_np 调用（src/ 全量搜索）；
- 客机 NSO：nn::os::SetThreadCoreMask 由 typed HLE 接管为**空实现**
  （nso_host_set_thread_core_mask 是 stub，不改掩码）；
- 客机导入解析是**严格白名单**（nso_call.c:resolve_import），sched_setaffinity 不在其中，
  客机拿不到这个符号；
- cgroup：进程在 cpuset:/vip，但同一 cgroup 下其它线程都是 0-7 => 不是 cpuset 收窄；
- 热降频：dumpsys thermalservice Thermal Status=0、电池 21 C、CPU 热区 52~65 C。

=> 收窄来自**系统侧**（厂商调度策略），不是本仓代码、不是客机、不是 cgroup、不是温度。
这条不重要——**关键是它只发生一次，不是每帧**，因此可以被"抢回"。

## 3. 实现（只改线程落在哪个核）

src/graphics/nvn_vulkan/engine/xbg_game.cpp，新增一个自包含的亲和性区块：

1. **拓扑识别**：读 cpuinfo_max_freq，取最快核为 prime，并算出次高档为 big cluster。
2. **异构闸门**：**只有存在两个不同频率档时才绑**（prime > second）。
   同构设备（例如最终目标 RG477M 这类全同构 SoC）不绑，保持系统调度，避免白白占死一个核。
3. **启动即绑**：gfx_worker_loop() 里 dm-gfx 线程启动后 sched_setaffinity 到 prime 单核。
4. **每帧复查**：perf_frame()（每帧）与提交路径末尾各复查一次掩码，被收窄就抢回；
   一帧一次 sched_getaffinity（约 1 us，相对 16 ms 的帧可忽略）。
5. **失败回退**：sched_setaffinity 失败就放弃绑核，保持系统调度。
6. **诊断开关**：live-set gfxaffinity=prime|big|off（默认 prime），并新增引擎侧分臂累计
   （NVN AB aff），模式切换时**重置测量窗口**，保证窗口不跨臂。

**渲染路径零改动**：git diff 只有 1 行被改写（提交路径追加一次掩码复查）+ 152 行新增；
不碰绘制、不碰 fence、不碰节拍、不碰游戏状态、不碰任何贴图/着色器。

**+38% 帧率、每帧 CPU 时间 -38%**，远超 L-029 的噪声阈值（跨进程噪声 +-3.5 fps）。

## 5. 持续压测与热/频证据

prime 模式连续跑 2 分钟以上（兵工厂深处，draws=602）：

- fps **43.8 ~ 48.7**，无衰减趋势；
- 掩码**恒为 0x80**、reassert=1（只在切臂那一次发生）=> 系统不是每帧收窄，抢回是稳的；
- cpu7 实际运行频率 **2.46 ~ 3.01 GHz**（多数时间顶到 3.014 GHz 上限），**无热降频**；
- 热区读数 52~65 C，与绑核前同量级。

标题画面（draws=39）全程 59.6~59.9 fps，绑核后同样稳。

## 6. 对上一轮归因的显式撤回

L-067 写的是"**游戏主线程** ffrs.gamewindow 在 cpu3~6 之间来回迁移"。
本轮线程级采样证明：主线程只占约 5%，真正吃满单核的是 dm-gfx；
主线程的迁移与帧率掉速**没有因果关系**。掉速的真实机制是
**dm-gfx 的核掩码被系统从 0xFF 收窄到 0x7F（被排除在超大核之外）**。
L-067 的"所有子域等比放大 = CPU 整体变慢"这一判读法仍然成立且是本次定位的入口，
但"主线程迁移"这一具体归因在此撤回。

## 8. 风险与可移植性

| 风险 | 处置 |
|---|---|
| 同构设备上白绑一个核 | 异构闸门：只有 >=2 个频率档才绑（heterogeneous=1 才生效） |
| 绑核失败 | sched_setaffinity 失败即回退系统调度 |
| 超大核长时间满载过热 | 实测 cpu7 2.46~3.01 GHz、热区 52~65 C，无降频 |
| 系统再次收窄掩码 | 每帧复查并抢回（实测 reassert 只发生一次） |
| 影响其它线程/系统 | 只改 dm-gfx 自身掩码，其它线程与 cgroup 不变 |
| RG477M（最终目标）行为未实测 | 代码按拓扑自适应；未在 RG477M 上验证，合入前必须补双机回归 |

## 13. 下一轮的入口：火场描述符开销分解

既然所有场景都 ≥ 40 Hz 已在 Honor 成立，下一轮要找的是**余量**，方向是 CPU 侧的描述符构建。
用引擎**自带的免改代码采样入口**取到（写 `files/gfx-cpu-profile` 文件，内容格式为
`<起始 present> <帧数> <detail>`，detail=1 开描述符分阶段计时；引擎每 30 个 present 轮询一次该文件，取完自删）：

```

```

火场（draws≈735、ops≈2150）60 帧的分阶段耗时（带仪表开销，实测 fps 从 55 掉到 47，
所以绝对值偏大，**看占比**）：

| 分段 | 60 帧合计 (ms) | 每帧 (ms) | 占比 | 调用次数/帧 |
|---|---|---|---|---|
| image_lookup | 157.6 | **2.63** | 29% | 6,941 |
| element_rest | 86.1 | **1.44** | 16% | 12,598 |
| set_finalize | 79.5 | **1.32** | 15% | 524 |
| buffer_bind | 46.8 | 0.78 | 9% | 5,657 |
| remaining（未归类） | 58.0 | 0.97 | 11% | — |
| texel_* 六段合计 | 69.4 | 1.16 | 13% | — |
| setup | 13.9 | 0.23 | 3% | 524 |
| memo_key / snapshot / verify | 25.5 | 0.42 | 5% | — |
| **合计（描述符构建）** | **547.4** | **9.12** | — | — |

三条关键结论：

1. **描述符构建是火场 CPU 的第一大项**（未插桩时 6.72 ms/帧，占 submit_cpu 14.4 ms 的约 47%），
   没有单一冒烟枪，是"千刀万割"式分布——单改一处只能拿到 10~20%。
2. **set cache 实际上已经完全不起作用**：日志里 `setcache hits=0.0`，516.2 次/帧全部被
   `fresh_skips=119.0` 与 `experiment_skips=397.2` 绕过；`set_finalize` 的 1.32 ms/帧
   主要是 **516 次/帧的 `vkUpdateDescriptorSetWithTemplate` 驱动调用**（0.91 ms）+ 动态偏移排序与打包。
3. **memo front 的主要拦路虎是 texel**：`why=texel493.4`（每帧 493 次因 texel 被排除），
   这正是第 2/3 轮（texel 池化 + 稳定 memo 键）试过并**实测净负**的方向。
   在改它之前必须先解释清楚：V2/V3 为什么净负、它们的额外开销落在哪一段。

因此下一轮（V5）建议的靶子与前置条件：

- 靶子：`image_lookup`（6,941 次/帧 × ~380 ns，主要是 img_cache 查找 + find_image + get_image
  + prepare_read 四段叠加）与 `element_rest`（每元素 12,598 次/帧）。
- 前置：任何改动都必须过 **L-032（不得弱化失效/清理）** 与 **显示回归**（引擎侧帧 dump，
  ≥90 帧 / 10 段 × 9 连续呈现帧），且按 L-029 以同场景交错 A/B 判定收益是否大于噪声。
- 风险提示：这几处都在"每 draw 重建描述符"的路径上，改错会直接表现为画面错乱或特效丢失，
  不适合在没有显示回归护栏的情况下试。

## 14. 第 6 轮开路：描述符 memo 的真正拦路虎（**不是键**）

第 5 轮收尾时把下一轮指向描述符路径（image_lookup 29% / element_rest 16% / set_finalize 15%）。
本轮把它拆开，结论与原先的假设**不一样**，因此单独成节。

### 14.1 火场每帧的事实（可复算）

| 指标 | 每帧 |
|---|---|
| set 构建次数 | 516.2 |
| 排除原因 texel（UNIFORM_TEXEL_BUFFER） | **493.4** |
| 排除原因 storage-image / storage-write / dynbuf | 14.9 / 6.0 / 0.9 |
| 描述符 memo 命中 / 未命中 | 353.5 / 0.6~1.1 |
| slot-local set cache 命中 | **0.0**（全被绕过：fresh 119.0 + experiment 397.6） |
| 描述符构建耗时（未插桩） | 6.72 ms/帧（占 submit_cpu 14.4 ms 的约 47%） |

### 14.2 撤回 V3 §10.12.2 的前提：「memo 键里其它分量每帧变」

V3 报告写的是「键里其它分量（UBO 地址等）每帧仍变 ⇒ 命中不了」，并把它列为重启 texel 方向的前置根因。
本轮实测**这条前提没有测量支撑**：

- 引擎自带的 keydiff 普查（`NVN PERF keydiff …`）在当前构建里**从不产生数据**：
  它只在 `hit==desc_memo.end()`（真未命中）时运行，而实战里 0.9/帧的「未命中」与
  `why[3]=dynbuf` 的**条目被拒**计数同数，六个拒绝原因计数器 `vwhy=blk/buf/ord/img/tex/stor`
  **全部为 0** ⇒ 根本没有真未命中 ⇒ 普查不触发（60 个采样窗口全 0）。
- 也就是说：**键不是拦路虎**。V3 的净负来自池化与 hit 路径的开销
  （descriptor build −1.12 ms，但 hit 路径 +0.92 ms、memo_key +0.53 ms 里大部分是诊断 census，
  另有未归项的池维护开销），不是键不稳定。

> **撤回依据**：§14.2 的两条实测（普查不触发 + vwhy 全 0）。

### 14.3 三个免重编译的运行时实验（live-set 切换，同会话同场景）

火场（draws≈735），每臂 5 个采样：

| 臂 | fps | submit_cpu_ms | memo_hits | set-cache 命中 | template 更新/帧 |
|---|---|---|---|---|---|
| ① 出货配置（基线） | 54.2~56.9 | 14.2~14.7 | 353.2~355.1 | **0.0** | 515.6~516.9 |
| ② `texelframe=1` | 53.7~55.6 | 14.6~15.2 | 353.2~354.6 | 0.0 | 515.5~516.3 |
| ③ `descmemo=0` | 53.8~55.7 | **15.3~15.4** | 0.0 | **363.7~367.3** | 504.9~505.4 |

三条结论：

1. **描述符 memo 在火场的总价值只有约 0.9 ms/帧**（submit 14.4 → 15.3），fps 差异在 ±1.5 噪声内。
   它服务 353 次命中/帧，但命中路径的复核/快照开销几乎抵消了收益。
   ⇒ **「把 493 次 texel draw 送进 memo」这条路的上限只有约 1 ms/帧，不是 6 ms/帧**。
2. **一项此前被掩盖的能力**：`descmemo=0` 时 slot-local set cache 命中 **367/帧**——
   它平时被 `experiment_cache_skip` 全量绕过（`desc_memo_enabled` 为真即绕过，
   `honorsetbypass` 这个 live 开关改不动它），而且比 memo 路径**便宜约 0.9 ms/帧**。
3. **两臂的 template 更新数几乎一样**（516 vs 505）⇒ set cache 的命中并没有替掉那 493 次 texel 构建：
   set cache 在 `descriptors_build` 内部，只省下 set 分配 + 模板更新，省不掉每 draw 的逐绑定工作。
   ⇒ 真正的大头就是 **493 次 texel draw 本身**。

### 14.4 texel 路径的真实代价（60 帧计时窗口）

| 站点 | 调用/帧 | 字节/帧 |
|---|---|---|
| texel-pending（全拷贝） | 401 | **8.57 MB（fullcopy）** |
| texel-CPU | 13 | 0.40 MB（copy） |
| storage-pending-fullcopy | 6 | 0.04 MB（zero） |
| storage-CPU-preserve | 3 | 0.14 MB（copy） |
| READBACK_TIMING 合计 | — | **alloc 9.32 MB/帧**、copy 0.55 MB/帧、zero 0.058 MB/帧 |

⇒ 每帧 401 次 texel view 申请 + 8.57 MB 全拷贝 + 9.32 MB 分配。

> **⚠ 更正（见第 15.1 节）**：本表取自 `gfx-cpu-profile` **插桩窗口**，
> 插桩使 `normal=false`，拷贝缓存被绕过 ⇒ **8.57 MB/帧 全拷贝是插桩假象**。
> 正常会话真值：texel **1.75 MB/帧**（真拷贝仅 3 次/帧、400 KB，其余是帧内复用命中）、
> **vertex 3.84~4.03 MB/帧 才是拷贝量的大头**。
> 同理，第 14.5 节的收益估计（「8.57 MB/帧 全拷贝降成脏区间拷贝」）**不成立**。

### 14.5 下一轮（V5）的精确假设与前置

**假设**：给 texel 绑定一个**跨 slot 存活的稳定 view**（持久 resident buffer + 脏区间增量刷新），
使 set 键稳定 ⇒ 已被证明能命中 367/帧的 **set cache** 就能覆盖这 493 次 draw
⇒ 省掉每次约 13 µs 的整表重建（上限约 6.7 ms/帧 ⇒ 火场 55 fps 上探 60 Hz），
同时把 8.57 MB/帧 的全拷贝降成脏区间拷贝。

**前置必答**：**texel 内容每帧到底改多少字节**。若几乎全改，增量刷新没有收益 ⇒ V5 直接死。
引擎已有现成计数器可测（`texelcopy` 的 copy_kb/wouldhit_kb、`wtrack` 的 dirty_pages_per_frame），
但当前火场里 `wtrack dirty_pages_per_frame=0.0`（写跟踪未生效），需要先把脏区间跟踪打开。

**门禁不变**：L-032（不得弱化失效/清理——resident buffer 的刷新必须精确覆盖来宾写入）、
显示回归（≥90 帧 / 10 段 × 9 连续呈现帧）、L-029（同场景交错 A/B，收益大于噪声才出货）。

> **⚠ 本节假设已被第 15 轮实测推翻**（见 15.1~15.3）：
> ① 收益估计里的「8.57 MB/帧 全拷贝」是插桩假象（正常会话 texel 只有 1.75 MB/帧）；
> ② 「上限约 6.7 ms/帧」不成立——补上稳定 view 后描述符 build 确实降了约 4.7 ms/帧，
> 但那是**中间计数器**；把整帧所有域加起来，净省约 **1.95 ms/帧**（中位数口径），
> 与 V1 报告（MAVIS-PERF-TEXEL-20261122.md）实测的「texmemo=0 快 1.86 ms/帧」同号同量级。
> ⇒ **这 1.95 ms 是重复收益**（引擎当前配置直接绑 guest 内存已拿到），不构成出货理由；
> **「让 texel 进 memo」这条路到此为止**，下一轮转向第 15.4 节的新靶子。

## 15. 第 7 轮：V5 靶子被实测推翻，memo 的一次真实翻盘（**不是**脏区间刷新）

第 6 轮把 V5 的假设写成了「给 texel 绑定跨 slot 存活的稳定 view（脏区间增量刷新），
让 set 键稳定、被已验证能命中 367/帧的 set cache 覆盖」，并把前置题定为
「texel 内容每帧实际改动多少字节」。本轮用引擎自带的运行时开关直接测了这个问题，
**结论与 V5 的假设不一样**，因此单独成节。

### 15.1 先更正第 14.4 节的数字：8.57 MB/帧 全拷贝是**插桩假象**

第 14.4 节那张表（texel-pending 401 次/帧、8.57 MB/帧 全拷贝、9.32 MB/帧 分配）
是在 `gfx-cpu-profile` 插桩窗口里取的。插桩让 `normal=false`，
于是 `texel_copy_cache` 的 `cacheable` 闸门失效、拷贝缓存被绕过
（`NVN PERF texelcopy normal=0` 全为 0 正是这个原因）。
**正常会话**下的真值（`NVN PERF uniform_trimmed_bindings` 同一条日志，火场、draws≈735）：

| 每帧 snapshot 字节 | 插桩窗口（§14.4 的来源） | 正常会话（实测） |
|---|---|---|
| vertex | — | **3.84~4.03 MB** |
| texel | 8.57 MB（实为插桩假象） | **0.04 MB** |
| storage / uniform | 0.04 / — | 0.50 / 0.52 MB |
| 合计 | 9.32 MB | ≈ 5.0 MB/帧 |

⇒ **texel 从来不是拷贝量的大头，vertex 才是**（占约 80%）。
第 14.5 节「把 8.57 MB/帧 的全拷贝降成脏区间拷贝」这个收益估计**不成立**。

### 15.2 V5 前置题（texel 内容每帧改多少）的实测答案

不用改代码：`gfx-live-set` 的 `texmemo=1` 会打开跨帧 resident 副本路径
（`texel_acquire`，用内容 hash 判断是否需要重拷），直接给出两个互斥计数：

- `texel_hits`：**内容未变**，直接复用上次的副本；
- `texel_refreshes`：**内容变了**，必须重新 memcpy。

火场（draws≈735）实测：

| 计数器 | 值（每帧） | 含义 |
|---|---|---|
| texel_binds | 257 | 走 resident 路径的 texel 绑定数（原路径 1068~1638） |
| **texel_hits** | **761~776** | 内容未变，直接复用 |
| **texel_refreshes** | **126.6~127.0** | 内容变了，重拷 |
| distinct / reused | 173 / 2.0 | 每帧不同区间数 / 其中上一帧也用过的 |
| fallback / evict | 17~21 / 17~22 | 退回逐帧快照 / 被淘汰 |

⇒ **约 84% 的 texel 读取是内容稳定的**（776/(776+127)），
脏区间刷新的**前提成立**。但**收益上限被 §15.1 掐死**：
texel 的拷贝量本来就只有 0.04 MB/帧，脏区间刷新能省的那点字节量微不足道。

### 15.3 机制确实有效，净省约 1.95 ms/帧——但那是被引擎用更便宜方式拿到的重复收益

`texmemo=1` 不只开脏区间刷新，它还让 UNIFORM_TEXEL_BUFFER 拿到
**跨 slot 存活的 view**（`texel_resident`，每 slot 一份），
于是描述符可以进 memo。对比同一会话同一场景的两臂（计数器类证据，不受机器快慢影响）：

| 指标（每帧） | 出货配置（texmemo 关） | texmemo=1 | 变化 |
|---|---|---|---|
| set 构建次数 | 516 | **264** | **−252（−49%）** |
| 描述符 memo 命中 | 353~356 | **605~608** | +250 |
| 描述符 memo 未命中 | 0.3~0.4 | **23.7~42.1** | +23~42 |
| memo 排除原因 texel | 493~494 | **199~218** | **−276~−294** |
| memo 排除原因 dynbuf | 0.3~0.4 | **27.1~27.5** | +27 |
| 描述符 build | 10.36~10.80 ms | **5.60~5.92 ms** | **−4.5 ms（−42%）** |
| 描述符 hit_total | 0.63~0.65 ms | **2.88~3.04 ms** | +2.4 ms |
| texel snapshot 字节 | 1.75 MB | **0.04 MB** | −1.71 MB |
| memo 复核拒绝 vwhy=tex / stor | 0.0 / 0.4 | **26.1~26.4 / 0.9~1.1** | 内容变了的条目被正确拒绝 |

**机制层面它是真的有效**：整表重建 516 → 264 次/帧，texel 排除 493 → ~200/帧，
描述符 build 砍掉 42%，而且被拒绝的条目正是「内容变了」的那些（vwhy=tex 26/帧）——
说明失效逻辑是精确的（L-032 语义没有被削弱）。

**但净账是负的**。把 `NVN PERF parts_ms_per_frame` 的**所有域**加起来（同口径对比）：

| 域 | texmemo=0（出货） | texmemo=1 | Δ（中位数） |
|---|---|---|---|
| descriptor | 8.92 ms | 6.95 ms | **−1.97** |
| hash | 0.08 ms | 0.29 ms | **+0.21** |
| snapshot | 2.62 ms | 2.27 ms | −0.35 |
| other / draw / cleanup | 6.61 ms | 5.96 ms | −0.65 |
| **域总和** | **17.13 ms** | **15.18 ms** | **−1.95 ms/帧（更快）** |

原因：`build` 这个中间计数器只统计「重建」那一段，**不含 memo 命中路径自身的复核成本**
（每帧 600+ 次命中，每次要复核注册版本、resident 代次、hash）——
这些成本落在 descriptor 域的其余部分和 hash 域里。
把两个口径放在一起看：`build` 省了 4.70 ms，但命中路径与 hash 吃回 2.73 ms，净省约 1.95 ms/帧。

⇒ **这与 V1 报告（MAVIS-PERF-TEXEL-20261122.md）的既有结论同号同量级**：
那一轮在 Honor 上实测 `texmemo=0` 比开着**快 1.86 ms/帧**（24.63 ms vs 32.87 ms），
所以引擎把 `texel_memo_enabled` 默认设成了 `false`（源码里那段注释记着这个数）。
本轮用**另一条路径独立复现了同一个数字**（1.95 vs 1.86 ms/帧），并补上了它的机理。

⇒ **但结论仍然是「不装」**：这 1.95 ms/帧是 **CPU 侧**的节省，
而当前火场 GPU 侧是 13.6~16.7 ms/帧、CPU 侧 15.9~20.3 ms/帧，
**CPU 仍不是唯一瓶颈**；更重要的是，引擎当前默认配置已经拿到了同样的收益
（直接绑 guest 内存、不做跨帧拷贝），而 `texmemo=1` 还要额外维护
每 slot 一份 resident 副本（live_mb 28 MB、holes_mb 28 MB、entries ~9000、evict 17~22/帧）。
⇒ **不为了 1.95 ms/帧去替换一条已经被证明更省的路**——那正是 V1 把它关掉的原因。

⇒ 对第 14.3 节的修正：第 14.3 节用 `descmemo=0` 测出的「memo 只值约 0.9 ms/帧」**方向是对的**，
但它没给出「memo 能省掉多少重建」的正面数字。现在这个数字有了：**4.70 ms/帧**——
**前提是补上跨 slot 存活的稳定 view**（第 14.3 节只换了 memo 开关，没有给 texel 稳定 view）。
⇒ 所以「让 texel 进 memo」这条路的**机制上限被量化了（约 4.7 ms/帧重建）**，
但**它已被引擎用更便宜的方式实现了**，重做一遍只会得到那 1.95 ms/帧的重复收益。

### 15.4 新的大头：snapshot 域（报告此前从未拆过）

`NVN PERF parts_ms_per_frame` 里有一个此前没人看的域：

| 域 | 每帧 | 每帧调用数 |
|---|---|---|
| **snapshot** | **2.25~2.74 ms** | **5866~7067** |
| descriptor | 6.94~7.34 ms | 1132~1388 |
| cleanup | 1.20~2.84 ms | 8.7~9.3 |
| draw | 1.50~1.64 ms | 735 |
| other | 3.01~3.24 ms | 9.8 |

snapshot 域的绝对值（2.25~2.74 ms/帧）与它 5866~7067 次/帧的调用量
（每次约 0.4 µs）说明它**不是**某条重路径，而是**海量小调用的累积**。
`NVN PERF v=1` 的 `snap_hit`/`snap_miss` 给出了它的规模。
**（第 16.1 节更正：本段原先写的「每帧约 3900 次命中、约 2027 次未命中」取自累计字段的差分口径不稳，
真实分解见第 16.1 节：每帧 7130 次调用 = 4837 次前端命中 + 16 次 map 命中 + 2277 次慢路径。）**

### 15.5 测量环境：今天这台设备处于热负载，fps 结论必须打折

本轮开工时设备状态：`load average 19.67`（8 核）、GPU 89.9°C、
Thermal Status=1、CPU0~2 频率降到 1.1~1.7 GHz（max 2.0）、CPU4~7 升到 2.4~3.0 GHz。
火场 fps 一度只有 42.7~47.3、submit_cpu 19.6~20.3 ms，
而健康状态下同一场景是 52.8~57.2 fps、submit 14.2~14.7 ms。
**submit_cpu 与 gpu_ms 同时等比放大约 25%**，是 L-067 的「整机变慢」签名。

⇒ 附带解释了一件旧事：**第 12.1 节那个被撤回的「41.0~43.4 fps 一次性下跌窗口」，
其数值形态与今天热负载下的窗口完全同形**（submit 18.2~19.1 / gpu 16.7~16.8
vs 今天 19.6~20.3 / 16.7~16.7）。
它不是场景特性，也不是「特效峰值」，而是**设备热/负载状态的产物**。
今天这次是**可复现地再次出现**，等于补上了当初缺的那条解释。

⇒ 因此本节**不写 fps 结论**（热负载下 fps 不可信），
只写**计数器类结论**（set 构建数、命中数、字节量、调用数——这些不随机器快慢变）。

### 15.6 交错 A/B 的方法论事故与净账结论

**先记一次自己的操作错误**：第一版交错 A/B 脚本的「关」臂写的是
`printf 'gfxaffinity=prime' > gfx-live-set`——但 `gfx-live-set` 是**整文件替换**语义，
没写到的开关保持当前值 ⇒ **`texmemo` 从来没被关掉过**，所谓「off 臂」其实一直在开。
（引擎日志里 `LIVE-SET` 只出现 `gfxaffinity=prime`，没有 `texmemo=0`，是它露出来的。）
第二版显式写 `texmemo=0` 才拿到真正的对照。

**这与 L-083 写的那条一致**：live-set 改完必须回读日志确认引擎真的应用了
（`LIVE-SET … at present N`），别假设「写了文件 = 引擎改了状态」。

**净账（两臂同口径，火场 draws 730~740，取中位数抗噪；on 臂 352 样本 / off 臂 844 样本）：**

| | texmemo=0（出货配置） | texmemo=1 | Δ（中位数） |
|---|---|---|---|
| descriptor 域 | 8.92 ms / 1385 次 | 6.95 ms / 1133 次 | **−1.97 ms** |
| hash 域 | 0.08 ms / 231 次 | 0.29 ms / 533 次 | **+0.21 ms** |
| snapshot 域 | 2.62 ms / 7047 次 | 2.27 ms / 5835 次 | −0.35 ms |
| 描述符 build | 10.28 ms | 5.58 ms | **−4.70 ms** |
| 描述符 hit_total | 0.62 ms | 2.86 ms | +2.24 ms |
| texel snapshot 字节 | 1.75 MB | 0.04 MB | −1.71 MB |
| memo 命中 / 未命中 | 353.9 / 1.0 | 606.1 / 41.7 | — |
| memo 排除 texel | 493.6 | 200.3 | −293 |
| **各域总和** | **17.13 ms** | **15.18 ms** | **−1.95 ms/帧** |

**读法**：省下的**重建**是真的（build −4.70 ms、set 构建 −49%），
但 memo 命中路径自己要付**复核成本**（每帧 600+ 次命中，每次复核注册版本、resident 代次、
内容 hash），这 2.24 ms 落在 `hit_total` 与 hash 域里；
两头相抵，各域总和净省约 **1.95 ms/帧**。

⇒ **与 V1 的既有结论同号同量级**（V1：texmemo=0 快 1.86 ms/帧；本轮 1.95 ms/帧），
**独立复现成功**。

⇒ **但本轮仍不出货**，理由不是「收益为负」，而是**这份收益引擎已经拿到了**：
出货配置直接绑 guest 内存（零拷贝、零副本维护），
而 `texmemo=1` 要额外维护每 slot 一份 resident 副本
（live_mb 28 MB、holes_mb 28 MB、entries ~9000、evict 17~22/帧、refresh 127/帧）。
为 1.95 ms/帧去换一条**已经被证明更省**的路，是 V1 把它关掉的原因，本轮不改这个决定。
⇒ **「让 texel 进 memo / 脏区间刷新」这条 V5 主线正式结束**（L-029：不占构建周期）。

**这一轮真正的收获不是某个版本，而是三件事**：
1. **第 14.4 节的 8.57 MB/帧 是插桩假象**（L-085），正常会话 vertex 才是拷贝大头；
2. **第 14.3 节「memo 只值 0.9 ms/帧」需要补充正面数字**：补上稳定 view 后，
   memo 能省掉的**重建**是 **约 4.70 ms/帧**（不是 1 ms），
   净省 1.95 ms/帧——但那 1.95 ms 是**重复收益**，引擎当前配置已经拿到了；
3. **新的靶子**：snapshot 域 2.2~2.7 ms/帧、每帧约 2000 次未命中、vertex 3.84~4.03 MB/帧（§15.4），
   以及那 493 次 texel draw 本身——它们现在是 memo 排除之外的**真实重建**，
   但要让它们可缓存，需要的正是 V5 那个已经被证明「机制有效、但不划算」的「跨 slot 稳定 view」。

**下一轮（V6）的入口因此改变**：不再追 texel 的缓存化，而是
① 给 snapshot 域那 2000 次/帧的未命中定价（哪些地址在反复失效），
② 重新评估 image_lookup / element_rest 这两个真正的大头（§13 的占比表）。
## 16. 第 8 轮（V6）：三条假设被实测否掉，描述符域被重新定价

第 7 轮把 V6 的入口指向 snapshot 域与第 13 节占比表里真正的两个大头。
本轮按「先算清、再定价、最后才动手」的顺序走，**结果是三条假设全部被数据否掉，本轮不出货**。

本轮设备仍处于热负载（load average 19.4~22.6、Thermal Status 1），
火场 fps 43.9~47.4（健康态 52.8~57.2）。因此本节**不写任何 fps 结论**，
只写计数器类证据与域级耗时证据（同口径、交错 A/B）。

### 16.1 先把 snapshot 域算清楚（更正第 15.4 节）

第 15.4 节写的「每帧约 3900 次命中、约 2027 次未命中」取自累计字段的差分口径不稳。
本轮用引擎自带的每帧计数器重新测，火场（draws 734~739）的真实分解是：

| 指标 | 每帧 |
|---|---|
| snapshot 调用总数 | **7130** |
| ├ 前端缓存命中（snap_front） | 4837 |
| ├ snapshots map 命中 | 16 |
| └ 慢路径（snapshot_slow） | **2277** |
| snapshot_invalidate 次数 | 697~700 |
| 其中真正擦掉的前端条目（erased） | **1.5~2.0** |
| 拷贝量（snap_site_bytes） | vertex 3.93~4.06 MB、texel 1.75 MB、storage 0.50 MB、uniform 0.52 MB |
| 请求量（snap_site_req） | vertex 6.30~6.35 MB |
| vcache | 命中 286~290/帧（免拷贝 2.87~3.04 MB）、填充 2.5~10/帧、重填 2.2~3.4/帧、条目 408~419、arena 19~249 MB（预算 256 MB）、flush 66~75 次 |

两条要点：

1. **每帧 7130 次调用中 4753 次是前端缓存命中**——前端缓存（8192 槽直映射）工作正常；
   真正的慢路径只有 2277 次/帧，且被 snapshot_invalidate 擦掉的条目只有 1.5~2.0 个/帧
   ⇒ **失效是精确的，不是「整表清空」**（这一点在 16.3 节差点被我自己读反）。
2. **vertex 是拷贝大头**：请求 6.3 MB/帧，实际拷贝 3.9~4.1 MB/帧，
   差额由 vcache 命中覆盖（2.9~3.0 MB/帧）。

### 16.2 假设一：vcache 的 volatile 封禁窗口 → A/B 证伪

**假设**：vcache::lookup() 里「内容在 3 个 present 内变化 ⇒ 置 VOLATILE 并封禁 300 个 present」
的规则，会让条目长期走全量拷贝；缩短或移除封禁窗口，可能消掉部分 3.9 MB/帧 的 vertex 拷贝。

**A/B（gfx-live-ab 写 vcache 强制关路径，运行时生效，交错 2 轮 × 2 臂）**：

| 臂 | fps | submit_cpu | gpu_ms | vertex 实拷 | requested vertex | snapshot 域 |
|---|---|---|---|---|---|---|
| r1 on | 45.83 | 19.03 | 14.39 | **3.90 MB** | 6.33 MB | 2.63 ms |
| r1 off | 44.01 | 19.81 | 14.57 | **6.35 MB** | 6.35 MB | 2.60 ms |
| r2 on | 44.83 | 19.64 | 14.54 | **4.06 MB** | 6.33 MB | 2.77 ms |
| r2 off | 46.51 | 18.99 | 14.44 | **6.35 MB** | 6.35 MB | 2.48 ms |

**结论：假设方向反了，机制本身有效但净收益为零。**

1. vcache **确实**在省拷贝：关掉后 vertex 拷贝从 3.90/4.06 MB/帧 涨到 6.35 MB/帧，
   即它省下 **2.29~2.45 MB/帧**。机制是有效的。
2. 但四个臂位的 submit_cpu_ms（18.99~19.81，极差 0.82 ms）与 fps（44.01~46.51，极差 2.5）
   **全部落在噪声内，而且方向自相矛盾**（r1 是 on 更快，r2 是 off 更快）。
3. **机理**：vcache 每次命中都要对**全部内容**逐字节算 FNV-1a（fast_buffer_hash）。
   它省下的 memcpy 只有 2.4 MB，按 40+ GB/s 算约 **50 µs/帧**；
   而哈希 2.4~3.0 MB 的成本与它同量级 ⇒ 两者相抵。
   ⇒ **缩短/移除 volatile 封禁窗口只会让哈希更多，不会更省**。
4. ⇒ **volatile 封禁窗口这条假设作废；vcache 整条路线退出 V6。**

### 16.3 假设二：692 次/帧的失效 → 前提读反了（这条差点让实验白做）

本轮原计划「用 snapinval 开关关掉失效，给 692 次/帧的失效定价」。
读源码时发现语义与设想相反：

`@cpp
void snapshot_invalidate(uint64_t address,uint64_t bytes){
    ++snap_invalidations;
    if(ab_off("snapinval")) ++snapshot_epoch;   // <-- 整表清空前端
    ...
    for(auto *m:{&snapshots,&uniform_snapshots}){ /* 只擦重叠条目 */ }
}
`@

源码注释写得很清楚：

> *"Every front entry mirrors a map entry of the same key, so an invalidation clears just the front
> slots of the map entries it erases; **bumping the epoch there (A/B target snapinval) emptied the
> whole front on every in-stream CPU write, overlapping or not.**"*

⇒ snapinval 是「把失效做成**最坏情况**」的对照开关，**不是**「关掉失效」。
**正常路径才是「只擦重叠条目」**（erased 仅 1.5~2.0/帧，16.1 节已实测）。

⇒ 这条路本身**已经被引擎做成最优**，没有可定价的收益空间；原实验设计的前提不成立。
（附带产物：引擎 gfx-live-ab 里还有哪些开关是「反向对照」，动手前必须逐个读源码确认。）

### 16.4 假设三：img_cache 被反复清空 → 净省 0.2 ms/帧，低于噪声底

**发现**：desc_memo_reset() 的第一行就是 img_cache.clear()
（除非 honor_img_cache_persist_experiment 为真）。而 desc_memo_reset() 每帧被调用约 **708 次**：

| 调用方 | 每帧次数 | 含义 |
|---|---|---|
| snapshot_invalidate() | 697~700 | 来宾对内存的 CPU 写入、事件信号、写回推迟等 |
| snapshot_reset() | 9.75 | **每次 submit 一次** |

⇒ img_cache 每帧被整表清空约 708 次 ⇒ 这就是 img_cache_misses 高达 244/帧 的原因。

**A/B（honorimgpersist=0/1，交错 3 轮 × 3 样本）**：

| 臂 | img_cache 命中 | img_cache miss | descriptor 域 | image 域 | submit_cpu | fps |
|---|---|---|---|---|---|---|
| persist=0 | 4419~4431 | 239~245 | 9.48~9.59 ms | 0.32~0.33 ms | 19.06~19.77 | 44.53~46.04 |
| persist=1 | 4657~4682 | **0.0** | 9.37~9.70 ms | **0.25~0.26 ms** | 18.93~20.20 | 43.87~46.55 |

⇒ miss 全部归零，但 **descriptor 域只动 0.06~0.13 ms、image 域 0.07 ms ⇒ 净省约 0.2 ms/帧**，
**低于本轮噪声底**（见 16.7 节）。而且现行实现下 img_cache 条目持有指向纹理池的
const RegisteredTexture*，跨池复用会悬垂，size()>4096 只是兜底闸门。
⇒ **不装**，但把「708 次/帧的整表清空」记为已知的结构性问题（L-092）。

### 16.6 方法论：分段归因没有插桩偏差（新增一个可用手段）

**疑问**：每个 DESC_SCOPE 都要读两次时钟，会不会把「调用次数多」的分段抬高，
让第 13 节的占比表失真？（第 15.1 节已经栽过一次「插桩假象」，这里必须先排除。）

**做法**：同一构建，gfx-cpu-profile 的 detail=1 与 detail=0 交错 3 轮，
比较 parts_ms_per_frame 的 descriptor 值：

| 轮 | detail=1 | detail=0 |
|---|---|---|
| r1 | 9.47 | 9.47 |
| r2 | 9.53 | 9.53 |
| r3 | 9.63 | 9.44 |

⇒ **完全一致，偏差不可测**（L-089）。

**机理**：① steady_clock::now() 的取时成本落在时间戳**之外**
（读时间戳之前的调用开销不计入被测区间）；② 子域时间以「根域 children」方式扣除，
根域独占时间对子域开销本身不敏感。
⇒ **第 13 节的分段表可信**，不需要按调用数打折。
⇒ 注意这与第 15.1 节是**两类不同的插桩污染**：那次是插桩**改变了被观测的行为**
（normal=false 让拷贝缓存被绕过），这次只影响**归因方式**，不影响归因结果。

### 16.7 瓶颈判定与本轮测量噪声底

| | submit_cpu | gpu_ms | fps | 帧周期 | GPU 占周期 |
|---|---|---|---|---|---|
| 当前（热负载） | 19.57~19.64 ms | 14.15~14.70 ms | 44.71~46.51 | 21.50~22.37 ms | **63~68%** |
| 健康态（对照 §12.1/§15.5） | 14.2~14.7 ms | 13.6~16.7 ms | 52.8~57.2 | 17.5~18.9 ms | 72~95% |

⇒ 当前设备上 GPU 只占周期的 63~68%，**CPU submit 占 88%** ⇒ 瓶颈在 CPU 侧。
⇒ 但**健康态下两者都接近饱和**（GPU 72~95%、CPU 79%）
⇒ 所以健康设备上 CPU 侧收益只能部分兑现，**≥3 ms/帧 的改动才值得占一个构建周期**。

**本轮实测噪声底**（vcache 四臂 + imgpersist 六臂）：

⇒ **在这台设备当前的热/负载状态下，CPU 侧 <1 ms/帧 的改动无法判定**（L-093）。
L-029 的门槛在热负载下要比常温更严，不是更松。

### 16.8 本轮结论与下一轮入口

**三条假设全部被实测否掉**：

| 假设 | 结果 | 处置 |
|---|---|---|
| vcache 的 volatile 封禁窗口可省 vertex 拷贝 | 方向反了；vcache 本就在省 2.3~2.5 MB/帧，但净耗为零（哈希 ≈ memcpy） | 作废，vcache 退出 V6 |
| 关掉 692 次/帧的失效可省开销 | 前提读反：正常路径已是按需擦除（erased 1.5~2.0/帧），snapinval 是「最坏对照」 | 作废 |
| img_cache 被 708 次/帧清空有代价 | miss 244→0，净省仅 ≈0.2 ms/帧，低于噪声底；且有悬垂风险 | 不装（记为 L-092） |

**仍然确认的事实**：

1. **描述符域占 submit CPU 的 48~49%**（9.41~9.63 ms/帧），
   其中约 **8.8 ms/帧是绑定解析的纯 CPU 工作**，驱动调用只占 1.16 ms。
2. snapshot 域（2.55~2.81 ms/帧）内部**没有剩余的低垂果实**：前端缓存工作正常、
   失效精确、vcache 净中性。
3. **描述符域没有单点冒烟枪**：8850 次绑定解析摊成每次约 760 ns，
   已知上限仍是第 15.3 节的 1.95 ms/帧（重复收益，V5 已退役）。
4. 分段归因**没有**插桩偏差，第 13 节的表可信（L-089）。

⇒ **本轮不出货**（L-029：没有超过噪声底的收益，不占构建周期）。
⇒ **下一轮（V7）的入口因此收窄成三条**：

- ① **先解决测量环境**：拿不到设备降温 + 前台独占的窗口，任何 <1 ms 的改动都判不了；
- ② **转 GPU 侧**：火场每帧 96 个 pass、82 个 render pass、735 个 draw，
  这是此前 7 轮从未碰过的维度（gfx-pass-profile 已有现成采样入口）；
- ③ 若仍走 CPU 侧，则必须找到 **≥3 ms/帧 的单点**，
  否则按 L-029 + L-093 应当停手，而不是继续在 760 ns 的均匀分布里找 1 ms。

## 17. 第 9 轮（V7）：**第一次拆开 GPU 侧**，并定位到一条 2.0 ms/帧 的写回成本

第 8 轮把入口收窄成「转 GPU 侧」。本轮用引擎**自带的免重编译入口**
`gfx-pass-live = "<帧数>"`（一次性逐帧 GPU pass 计时）拿到了本项目**第一份 GPU 侧分解**，
并把一条此前没人看过的 **2.0 ms/帧** GPU 成本**用排除法钉死**。

**本轮仍不出货**：找到的是靶子与机理，改动涉及写回正确性路径（L-032），
在当前热负载设备上无法做可信的显示回归。改动方案见 §17.6，留给第 10 轮。

### 17.1 采样入口与可复现性

`gfx-pass-live` 是一次性标记（读后即删），格式为帧数；它把
`pass_prof_enabled` 打开、`pass_prof_period=1`，在接下来的若干帧里
给每个 render pass / compute dispatch 写一对 BOTTOM_OF_PIPE 时间戳。

每个 pass 的耗时 =（pass 末尾时间戳 − pass 开头时间戳）。
**注意**：pass 开头的时间戳写在 BOTTOM_OF_PIPE，所以它取到的是「GPU 把之前的工作排空后」的时刻；
因此该值**包含 pass 内部可能的 GPU 空闲**，但**不包含** pass 之间的空档。

**可复现性（5 帧，火场）**：

| pass | 各帧实测 (µs) | 极差 |
|---|---|---|
| G-buffer（att=7，242 draws，585504 verts） | 2366 / 2363 / 2372 | **9** |
| 同几何第二遍（att=1，246 draws，585642 verts） | 749 / 743 / 749 | 6 |
| 离群全屏 pass i=13 | 600 / 602 / 608 | 8 |
| 离群全屏 pass i=17 | 422 / 422 / 429 | 7 |
| 后处理链（40 个同 shader 的 pass） | 23~31 每个 | — |

⇒ GPU 侧的计时**比 CPU 侧稳定得多**（极差 6~9 µs），
这与第 16.7 节的 CPU 噪声底（0.82~1.11 ms）形成鲜明对比：
**GPU 侧的数字在热负载下仍然可信**（比值类结论），这是本轮能出结论的前提。

### 17.2 第一个 GPU 侧基线

**内部渲染分辨率是 768×436**（不是显示坐标的 3000×1920）——96 个 pass 里 **71 个**是这个分辨率。
火场每帧：96 个 render pass、735 draw、135 dispatch、2107 条 NVN op。

GPU 侧一帧的账（5 个被采样的 slot）：

| 组成 | 耗时 |
|---|---|
| render pass 合计 | 9.86 ms（96 个 pass） |
| compute dispatch 合计 | 3.18 ms（≈135 次） |
| **落在 pass/dispatch 之外的空档** | **2.13 ms** |
| 合计 | 15.07 ms ≈ `gpu_ms` 14.7~15.1 ✓ |

**集中度**：**top 4 个 pass 占 pass 总时长的 53%**（5202 / 9857 µs）：

| us | slot/i | 分辨率 | att | fmt | draws | verts | 备注 |
|---|---|---|---|---|---|---|---|
| **2366** | 6/6 | 768×436 | **7** | 122 | 242 | **585504** | G-buffer（顶点着色器 7a4358322ae60f0e） |

两条关键结构事实：

1. **同一批几何每帧被光栅化两遍**：585504 与 585642 顶点、242 与 246 个 draw，
   一次进 7 个 attachment 的 G-buffer（2366 µs），一次进 1 个 attachment（749 µs）。
   两遍合计 **3115 µs = 32% 的 GPU pass 时间**。
2. **每 pass 的固定开销基线 ≈ 23 µs**：有 **40 个** pass 用的是同一个 shader 对
   （1e222af40b26bd25 / 9b0acd9875f7c44a），每个 23~31 µs、每次 1 个 draw、36 个顶点
   —— 这是"一个全屏三角形 pass"在 768×436 上的正常成本（约 14.5 Gpx/s）。
   96 个 pass × 23 µs ≈ **2.2 ms/帧 是纯 per-pass 固定开销**。

| pass | us | 结构 |
|---|---|---|
| i=13 | **600 / 602 / 608** | att=2, fmt=122, 1 draw, 3 verts |

⇒ 成本不在 pass 结构或分辨率里，而在**片元着色器读了什么**（采样数 / 采样源是否刚被写过），
或该 pass 的 attachment 的 load/store 方式。本轮未定位，留作后续。

### 17.4 **2.0 ms/帧 的 GPU 空档**：位置、稳定性与共变关系

`span_us` 的定义是「**第一个**记录项的 q0 → **最后一个**记录项的 q1」，
而 `pass_us` / `compute_us` 是各记录项自身的时长。
⇒ **span − pass − compute = 落在所有 render pass 与 compute dispatch 之间的 GPU 时间**
（barrier、缓冲拷贝，或 GPU 空闲）。

跨 5 帧、5 个 slot 的实测：

| 每 slot 的 compute dispatch 数 | 空档 |
|---|---|
| 1 | 0 µs |
| 3 | 2~3 µs |
| 14~15 | 94~100 µs |
| **115** | **2011 / 2023 / 2028 / 2030 / 2032 µs** |

**跨帧极差 ≤ 21 µs**，且**与该 slot 的 compute 工作量无关**
（compute_us 在 1518~2189 µs 间变动时，空档稳定在 2020 µs）。

⇒ 这是一条**稳定的固定 GPU 成本**，不是波动。

### 17.5 决定性排除：这 2.0 ms **不是**「GPU 等 CPU」

最自然的替代解释是：CPU 是瓶颈（19.6 ms/帧），GPU 追上来后**空转等待**。
若是如此，给 CPU 加负担就会把这段空档**撑大**。

用运行时开关做交错 A/B（`descmemo=0`，第 14.3 节实测会让 submit_cpu **+0.9 ms**）：

| 臂 | submit_cpu | fps | **那个 2 ms 空档** |
|---|---|---|---|
| base r1 | 17.78 | 49.4 | **2028 µs** |
| slowcpu r1 | 19.06 | 45.7 | **2022 µs** |
| base r2 | 18.81 | 46.8 | **2032 µs** |
| slowcpu r2 | 19.09 | 45.5 | **2031 µs** |

⇒ CPU 多干了 **1.28 ms/帧**、fps 掉 **3.6**，而空档**纹丝不动**（2028 / 2022 / 2032 / 2031）。
⇒ **「GPU 空转等 CPU」被排除**（若成立，空档应涨约 1.3 ms）。
⇒ 这 2.0 ms 是**真实发生在 GPU 上的工作**。

### 17.6 归因：存储写回路径的 9.32 MB/帧

三条独立证据指向同一处：

**① 引擎自己的读回计数器**（`gfx-cpu-profile detail=1`，60 帧窗口）：

`
NVN READBACK_TIMING alloc_bytes=559122340 copy_bytes=46815768 zero_bytes=3505548
                        guarded_bytes=0 noncoherent_flushes=0
`

⇒ **分配了 9.32 MB/帧 的读回缓冲**（`readback_alloc` 430 次/帧），
其中只有 0.78 MB/帧 是 CPU 侧拷进去的内容，**其余 ~8.5 MB/帧 是 GPU 写进去的**。

**② 写回的实际搬运量**（`NVN PERF cleanup_ms_per_frame`）：
`writebacks=0.64 ms (7.1 MB)`（设备空闲时）/ 2.58 ms（高负载时）
⇒ **7.1 MB/帧** 的 GPU 结果经 **host→host memcpy** 回写到来宾内存。

**③ 带宽核对**：
读回缓冲分配在 **HOST_VISIBLE | HOST_COHERENT | HOST_CACHED** 内存上
（`xbg_game.cpp` 的 arena 选择逻辑），所以 **GPU 是直接往主机可见内存里写**：

| | 字节 | 耗时 | 带宽 |
|---|---|---|---|
| GPU 写主机可见内存 | 9.32 MB | **2.0 ms** | **4.66 GB/s** |
| CPU memcpy 同样字节 | 7.1 MB | 0.64 ms（冷） | 11 GB/s |

⇒ **GPU 往主机可见内存写，比 CPU memcpy 还慢 2.4 倍** —— 这是移动 GPU 写 host-visible
（非 tile、非压缩、不可缓存）内存的典型代价。
⇒ 9.32 MB ÷ 4.66 GB/s ≈ **2.0 ms**，与 §17.4 实测的空档**数值吻合**。

**⇒ 结论：每帧有 9.32 MB 的 GPU 结果被写进主机可见内存，代价 ≈ 2.0 ms GPU 时间**
（占 GPU 帧的 14%、整帧周期的 9%），外加 CPU 侧 7.1 MB 的 host→host memcpy
（0.64 ms 冷 / 2.58 ms 热）—— **合计 2.6~4.6 ms/帧，占整帧的 12~20%**。
这是 9 轮以来**第一条不依赖任何重复收益的、量级够大的 GPU 侧靶子**。

**三个候选修法（都动画面吗？都不动，但风险不同）**：

| 方案 | 收益 | 风险 |
|---|---|---|
| **A** 写回目的地改 device-local，退役时补一次 device→host 拷贝 | GPU 侧 2.0 → 约 0.9 ms（估算） | 新增一条拷贝与一道屏障；pending-view 语义必须一字不变（L-032） |
| **B** 写回改成惰性：guest 真读到该区间时才拷 | 若 guest 不读，可省掉整条 7.1 MB | 要把 `cpu_access` 变成写回触发点；必须保证 guest 读到的值与现在一致（L-032） |
| **C** 让来宾的存储缓冲直接用 HOST_VISIBLE 分配 | 省掉 CPU 侧 0.64~2.58 ms 的 host→host memcpy | GPU 侧 2.0 ms 仍在；且来宾缓冲由游戏自己分配，引擎不掌控 |

⇒ **第 10 轮的入口就写在这里**，且必须带**显示回归**（≥90 帧 / 10 段 × 9 连续呈现帧）
与 **L-032 复核**：写回的值、时机、失效语义必须与现在**逐字节一致**。

### 17.7 附带确认的一件事

引擎注释里记着一条重要的旧账：
*"~2200 begin/end pairs per D2R camp frame cost the Adreno 730 ~10 ms of GPU time and ~4 ms of CPU"*
（每 draw 一个遮挡查询的旧做法）。实测当前是**批量模式**：
`occlusion=155.7 次/帧`，不是 2200 ⇒ **这条 ~10 ms 的大头引擎早已修掉**，
不需要再查。同时每帧还有 `barriers op27=448.9` 次来自 compute dispatch 的屏障
（`compute_barrier`，dst mask 含 ALL_GRAPHICS|ALL_COMMANDS），
其 dst stage 是否也可以延后到 compute 段末尾才发，是 §17.4 空档归因的**备选解释之一**
（当前更可能是写回搬运，但两者都指向同一个 slot，尚未彻底分开）。

### 17.8 本轮结论

1. **第一次拿到 GPU 侧基线**：内部分辨率 768×436、每帧 96 个 render pass、
   GPU pass 时间集中在 top 4（53%）、同一批几何每帧被画两遍（32%）、
   每 pass 固定开销基线约 23 µs。
2. **两个离群 pass**（600 / 425 µs，同结构基线 63 µs）已定位到"片元读什么"，未定位根因。
3. **2.0 ms/帧 的 GPU 空档**已用排除法钉死为**真实 GPU 工作**（不是等 CPU），
   并用三条独立证据归因到**存储写回路径的 9.32 MB/帧 GPU→主机可见内存写入**。
4. **本轮不出货**：改动落在写回正确性路径（L-032），
   且当前设备处于热负载，无法做可信的显示回归 ⇒ 按 L-029 不占构建周期。
