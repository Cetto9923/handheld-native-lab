## 3. 待验证假设（按证据强度排序）

### H1（首选）：深度附件采样复用路径在 Mali 上产生逐帧未定义内容

**证据链：**

1. `gfx-depth-aspect` 标记当前值 `auto` → 走**设备默认**。
2. 源码 `xbg_resolve_depth_aspect()`：`depth_aspect_enabled = !honor`。
   Honor 判定是 `FFRS_PROFILE_TABLET=1 && vendorID==0x5143 && deviceName=="Adreno (TM) 735"`。
   **RG477M 是 Mali-G615，不匹配 → `honor=0` → `depth_aspect_enabled=1`**。
3. 设备启动日志实测：`NVN depth-aspect sample reuse=1 (honor=0; marker (device default))`。
4. 源码注释明确记录该路径的已知缺陷：
   > `// Adreno 735: reusing the open depth/stencil pass flickers the moon halo in the real scene.`
   > `// device default is off on the Honor tablet, because that path was measured to flicker the moon halo`

   即：**同一条复用路径在 Adreno 上被实测为闪烁并因此关闭，但在 Mali 上仍然是开的。**
5. 该路径的行为是：深度附件作为采样源被复用时**跳过**原本需要的
   `end_open_pass()` + 全屏障（`prepare_read()` 中 `keep` 分支直接 return）。
   在 TBDR（Mali）上，结束一个带深度的渲染通道会强制把附件 write out 再 read back；
   跳过它意味着**深度内容是上一帧的残留或未定义的**，被采样进着色器后逐帧变化。

**这条假设能解释全部现象**：内容原地变化（不是滚动）、连续 183 个亮度级别（不是两态）、
局部而非全局（只有读深度的绘制受影响）、与相机和 HUD 无关。

**但它还没有被真机 A/B 证实。** 需要的实验：

```
# 关闭深度附件采样复用
echo -n "0" > /sdcard/Android/data/org.ffrs.gamewindow/files/gfx-depth-aspect
# 重启游戏进程后进入同一场景同样位置，抓 10 秒录像，同样做 2.3 的像素簇统计
# 若像素簇 std over time 从 13.32 降到 ~0，则 H1 成立
```

对照组：`gfx-depth-aspect` = `1`（现状）。注意标记值 `0` 会被读作
`buf[0]=='0'` → `depth_aspect_enabled=false`；`auto` 走设备默认（=开启）。

**注意**：标记只读不写，`xbg_resolve_depth_aspect` 在启动时读取一次，因此必须重启进程。

## 7. 2026-11-13 晚间续查：特征纠正 + 7 条引擎侧路径全部证伪

### 7.1 闪烁的准确形态（此前记录有误，此处纠正）

用引擎逐帧 CSV（`codex-frame-12966.csv`，52200 行）与同窗口录像对齐后发现：

- 此前「183 个连续级别、单峰非双峰」的结论**是短窗口假象**。在 351 帧窗口里，
  视口逐帧均值稳定落在 **87.6~87.9** 与 **85.9~86.1** 两个档，**暗帧占比 35%**。
- 之前只验证了**黑边**（y0..119、y840..959 std=0.000）就宣布「排除全屏亮度闪烁」，
  这只证明黑边不闪，**没有**证明视口内部不闪。
- 全局增益拟合 `dark ≈ 0.981*bright - 1.703` 只解释亮暗差的 **0.5%** 方差
  → **不是全局曝光跳变**，是局部叠加。
- 亮/暗两帧放大对比：亮帧地面呈**冷蓝、发白、对比被抬平**；暗帧地面呈**暖棕、纹理更锐利**。
  差异图显示变化集中在**主角左侧的鹅卵石广场**（最大块 y480..520 x640..680，
  逐块平均差 52.2 灰阶）。
- 相邻帧 MAD 呈**奇偶交替**（≈2.0 / ≈0.35）：一半帧是大变化帧，一半帧几乎与前帧相同。

### 7.2 已证伪的引擎侧路径（全部为同机位、同存档、引擎自己产的逐帧指标）

指标 = 主角左侧地面 ROI（x 230..520, y 430..650）的**逐像素 std over time**；
「暗帧占比」= 视口逐帧均值低于中位数 0.5 以上的帧比例。

| 档位 | 开关 | ROI std | 暗帧占比 | 结论 |
|---|---|---|---|---|
| 基线 | 设备默认（reuse ON） | 11.82 | 35% | — |
| A | `gfx-depth-aspect=0`（深度附件采样复用关） | 10.52 | 33% | **证伪**（仅 −2.2%） |
| B | `gfx-indexed-resident=0` + `gfx-no-texel-memo=1`（同时关） | 9.47 | 37% | **证伪**（暗帧占比未降） |
| C | 运行时 `descmemo` 关（描述符缓存） | 10.94 | 27% | **证伪** |
| D | C + `imgcache` 关（图像缓存） | 11.17 | 35% | **证伪** |
| E | D + `xmemo` + `bindcache` 关 | 10.05 | 40% | **证伪** |
| F | `gfx-bright` 色调映射 LUT 改写 | `NVN PERF bright applied=0.00 k=1.00` | — | **本场景根本没生效，排除** |

C/D/E 三档用的是引擎自带的**运行时热开关** `files/gfx-live-off`
（每 30 帧轮询、只关不开），**同一进程、同机位、同一存档**内连续录 4 段对比。

→ **结论：闪烁对深度复用、GPU 常驻索引/间接路径、texel 常驻副本、描述符缓存、
图像缓存、跨帧 memo、绑定缓存、tone-mapping LUT 全部不敏感。**
根因不在引擎的缓存与调度层。

### 7.3 与荣耀树「月亮光晕」缺陷的考古（重要线索，仍未闭合）

荣耀树 `coordination/HANDOFF.md` 记录过一次**同型**调查（提交 `0052889`）：

> 月亮光晕逐帧两态跳变（区域均值 82.2 ↔ 103.0）；引擎每帧提交的 draw、
> 间接参数、纹理签名**逐字节相同**；闪烁**只存在于 GPU 常驻间接/索引路径**；
> 走客机内存路径则稳定但每帧同步 GPU（33.3 ms legacy wait → 10 FPS）；
> `7b733b9`（只服务当前 slot 的间接模板）能消除闪烁但**未发布**（代价同上）；
> 根因收敛到「compute 写出的顶点/实例数据，间接路径从引擎会复用的缓冲读、
> 客机路径读的是已解析副本」，**未修复**，当时的下一步是 GPU 级抓帧。

本轮在 RG477M 上复现的地面闪烁与它同型：两态跳变、引擎提交内容逐帧恒定、
局部软光区域整体出现/消失。

**因果链（本轮新发现）**：旧构建里遗留的 `gfx-pass-profile` 标记让 `pass_prof_enabled`
整个会话常开 → `indexed_graphics_ready()` 每帧都拒绝 → **GPU 常驻索引路径被意外关掉**
→ 潜伏缺陷看不见。性能修复 `0228e3c` 把这个标志改成**帧作用域**
（`pass_prof_active()`）后，快路径恢复 → 潜伏缺陷显形。
（`0228e3c` 本身经复核是正确的性能修复，30 FPS 不回退，不撤销。）

### 7.4 本轮新增的诊断能力（提交 `e6de229`，分支 `task/T-rg477m-flicker-liveoff-20261113`）

`gfx-live-off` 原本能热关 8 个缓存，但**唯独缺了最关键的 GPU 常驻索引/间接路径**
（只能靠启动标记切），间接参数来源 4 档也只能靠启动标记切，于是荣耀树的四档矩阵
每档都要重启 + 走回场景。本次补上：

- `gfx-live-off` 新增令牌 **`gpuidx`**：运行时同时关掉 GPU 常驻索引绘制与
  GPU 常驻间接模板查找，与启动标记 `gfx-indexed-resident=0` 语义一致。
- 新增标记 **`gfx-live-indirect-mode`**（0..3）：运行时选择间接参数来源，
  与启动标记 `gfx-indirect-mode` 同语义，可在**一次会话**里跑完整矩阵。

两者均为只读诊断、默认关、**不改变任何默认行为**；`scripts/verify_host.py
--runtime-contracts` 退出码 0。

### 7.5 剩余判别实验（进行中）

根因只剩两种可能，必须用**引擎自己呈现的那一帧**（合成前，含 alpha 通道）来切：

- ① 引擎画出来的帧本身就在两态之间变 → 问题在客机/引擎渲染；
- ② 引擎呈现的帧稳定，但屏幕上是两态 → 问题在呈现/合成（alpha、blit、合成器）。

工具：引擎 probe 设施，`files/gfx-codex-probe` = `4` → `probe_present()` →
`probe_snapshot()` 导出 present 图像的完整像素与中心 ROI（含 alpha 字节）。
（marker 必须在进程启动前存在，故需重启一次；这是唯一需要重启的理由。）

## 8. 2026-11-13 续：闪烁的空间定位与引擎侧取证准备

### 8.1 先澄清两件被我的测量工具污染的事

- **引擎没有掉帧。** 帧计数器对墙钟实测（不录屏、不武装任何标记）：帧号 15240 -> 15420，
  `monotonic_ns` 跨度 5.9975 s -> **30.0 FPS 精确稳定**；同时 `NVN PERF` 报 fps=29.99/30.01，
  sync_wb=0，sync_rb=0。
- **用户看到的掉帧严重来自我的诊断工具叠加**，不是游戏缺陷：
  - `screenrecord --bit-rate 12000000` 录 1280x960 本身会压帧；
  - 同时武装 `gfx-pass-live=150` 会让引擎对**每个 draw** 拼 shader 串并往 engine.log 灌行
    （本轮已灌 5 万行 `NVN GPASS`），实测把帧率压到 **10 FPS**（帧间隔 100 ms）。
  - 干净对照：`plaza_base.mp4` 447 帧 / 14.95 s（帧间隔中位 33.1 ms，满 30.2 FPS，未武装 pass-live）；
    `flick.mp4` 135 帧 / 14.0 s（100 ms/帧，叠加态）。
  - 结论：`gfx-pass-live` 是**诊断开销**，不能与性能测量同时开。后续性能测量一律用
    「帧计数器 + PERF」，不用录屏。

## 10. 2026-11-13 夜：闪烁机制被量化锁定为「覆盖层两态」（引擎侧呈现帧口径）

### 10.1 「亮帧」其实是「糊帧」

对 9 帧逐帧计算各区域的亮度均值与拉普拉斯方差（锐度）：

| 区域 | 亮度范围 | 锐度(lapvar)范围 | corr(亮度,锐度) |
|---|---|---|---|
| 铺石地面 x300..700 y380..540 | 141.5..151.0 | 281.8..409.2 | **-0.996** |
| 白色栏杆/墙面 x420..700 y285..340 | 100.4..104.9 | 262.1..302.4 | -0.729 |
| 水面 x950..1250 y90..240 | 43.5..44.8 | 1491..1503 | +0.914（动画粒子） |
| 小地图 x1060..1250 y20..260 | 37.4..38.0 | 2897..3053 | +0.781（UI 动画） |
| 夜空（无纹理）x600..900 y20..120 | 114.23..114.53 | 49.16..50.07 | 稳定 |

→ 铺石区的**亮度与锐度严格反相关**：锐度 409/407/404/402 的帧亮度 142.2/141.9/141.6/141.5（暗），
锐度 290/290/289/288/282 的帧亮度 151.0/151.0/150.8/150.7/150.7（亮）。
**「亮」=「糊」**，不是真的变亮了。

### 10.2 不是重采样 / 分辨率差异（关键否证）

对最锐帧与最糊帧做铺石区 200×160 径向平均功率谱，比值（糊/锐）：

```
f=4  0.683   f=8  0.805   f=12 0.653   f=16 0.770   f=24 0.680
f=32 0.646   f=48 0.685   f=64 0.697
```

→ 比值在 f=4..64 **几乎是常数 0.68**。若是 mip 层级切换或内部渲染分辨率变化，
高频必须急剧衰减（ratio→0）。平坦的比值意味着**全频段等比缩放 = 对比度被压缩**，
外加一个整体抬亮的偏置。

### 10.3 是「半透明亮层覆盖」的数学特征

row 470 逐像素剖面（锐帧 → 糊帧）：

```
sharp 140 141  85 138 146 121 144 157 155 177 135 179 154 168 180 149 125 127 168 123 100 153 148
blur  144 147 103 145 151 133 155 164 162 179 148 187 180 184 190 170 153 148 177 145 121 158 152
diff   -4  -5 -17  -7  -5 -11 -10  -6  -7  -1 -13  -8 -25 -15 -10 -21 -27 -21  -8 -22 -21  -4  -4
```

→ **暗像素抬升最多（85→103，+18），亮像素几乎不动（177→179）**。
这是「一层半透明亮色覆盖层乘性压暗对比」的签名；纯加性叠加做不到（加性会让差值与原值无关地恒定）。
3×3 线性核拟合两态关系 R²=0.885/0.913，核带负旁瓣（非单纯低通），同样指向混合/合成而非重采样。

并排放大图（present 20460 锐 vs 20468 糊）可见：**糊帧整体像罩了一层半透明白纱**，
石缝被填平、角色也被冲淡；锐帧石缝锐利、角色实心。

### 10.4 由此得到的机制结论

**闪烁 = 某个半透明/加性覆盖层在场景颜色靶上逐帧「出现 / 消失」**（不是纹理重采样、
不是全局曝光跳变、不是合成层问题）。这也解释了此前所有「证伪」结果：深度复用、
GPU 常驻索引/间接、texel 常驻、descmemo/imgcache/xmemo/bindcache、tone-mapping LUT
都不负责「画这层覆盖」。

引擎侧已有现成工具可以回答「是哪一个 draw」：Honor 树为篝火调查开发的 **逐帧 draw census**
（`gfx-flame-diag`），每帧输出：

- `FLAME_FRAME fr=<present> ... pmean=... rtpx=... rtw=... rth=...`
- `FLAME_DR fr=<present> part=.. pmem=.. <vs>:<fs>:<P|o>:<draws>:<instances>`（该帧每个 draw 的
  顶点/片元着色器对、颜色靶、draw 次数、实例数；P=呈现靶）
- `FLAME_EV fr=<present> ...`（场景颜色靶上的有序事件流：draw / colour clear / depth clear /
  copy dst / resolve dst —— 可区分「画完被 clear 覆盖」的 H2 与「GEQUAL 深度拒绝」的 H1/H4）

该 census 原为 Honor 场景硬编码着色器键，**但 draw 普查与事件流是通用的**。

1. **通用运行时开关** `files/gfx-live-set`：内容为 `name=value` 空格分隔，可在**不重启**的前提下
   实时切换 15 条引擎内部路径（texdirty / texmemo / imgcache / descmemo / dynpartial / xmemo /
   bindcache / ownedinput / gpuindexed / uppro / depthaspect / pipefast / pipememo / occlusion / vcache）。
   这把此前「每条路径要重启一次」的矩阵变成一次会话内可跑完的矩阵。
2. **强制 `maxLod=0` 诊断**（`mipmaxlod0=1`）：所有采样器都不再选 mip。若闪烁消失 ⇒ 直接证明
   是 mip/LOD 翻转；若仍在 ⇒ 排除 mip，剩下的就只有顶点/UV 数据与绑定缓存。

### 11.6 未声称

闪烁的最终根因仍未锁定，未做任何修复；不声称完整游戏兼容、60 FPS 或独立 QA。

### 13.2 完整 census 下的结论（45 帧，512 容量，over=0）

- 两态的 draw 条目**集合完全相同**：共同 80 条，各自独有 0 条；
- 有序列表（按 log 的 part 序号重排后）：SHARP 内 10/136 对完全相同、BLUR 内 48/378、跨态 56/476 ——
  **跨态并不比态内更不一致**；
- 没有任何 draw 条目的每帧计数能预测状态：点二列相关 |r| 全部 ≤ 0.2；
- `FLAME_FRAME` / `FLAME_Z` 的**全部字段**（含十六进制的 texhash/rthash/c5a/c5b/c5c/c2a/c0a）
  无一能分离两态。`pmean`/`rtpx` 表面「完美分离」是**采样点恰好不重合**造成的伪相关，
  两者值域大量重叠（SHARP pmean 6771673..7066858 vs BLUR 6661311..7071042），`pf` 直接重叠 8 次。

### 13.3 白纱的量化（引擎呈现帧，ROI=x260..560 y400..540 纯鹅卵石，排除主角）

- 白纱强度：30 个 BLUR 帧的 alpha = **0.0775 ± 0.0120**（min 0.0500 / max 0.0927），R² = 0.88；
- 相邻 BLUR 帧的 alpha 图相关 r = **0.86 ~ 0.99** ⇒ 是**一个离散的连贯状态**，不是逐帧随机抖动；
- alpha 在 ROI 内**不均匀**：从左侧 0.02~0.06 渐变到右上 0.12~0.15；
  alpha 与 SHARP 帧局部亮度相关 r=+0.27、与勾缝线高频相关 r=+0.20；
- 相机零位移（天空/横幅最佳整数位移搜索 err@0 即最优 dx=0 dy=0）；
- 天空/水面/UI 横幅**完全不变**，地面、台阶、主角被覆盖；
- 引擎内部 8b27 场景渲染目标上的亮像素计数也随状态变化 ⇒ 差异**在引擎渲染阶段**就存在，
  不是呈现/合成阶段。

### 13.6 新增诊断：逐 draw 的 uniform 绑定指纹追踪
