## 3. Q1：一次场景切换的时间去哪了（四段拆分）

「超出时间」＝该窗口墙钟 − 稳态 60 帧（60 × 33.33 ms）。四段分别是：
- **着色器加载**：该簇内着色器载入耗时（慢载入行自带帧号，其余按帧锚点归属，单次误差 ≤ 5 ms）

- **提交阻塞**：`submit_cpu_ms`（CPU 在 vkQueueSubmit 内）与 `block_ms`（gpu_sync / legacy_wait 等阻塞点）

1. **测试者猜的「加载着色器」只在最坏的一簇成立（W84-87，26.5%），在两笔更大的切换里不成立**（W92-94 2.6%、W25-26 1.9%）。
2. **引擎侧最大的单笔是提交路径**：切换窗口里 CPU 在 vkQueueSubmit 内的时间 32.7–37.7 ms/帧，是稳态 10.5 ms/帧的 **3.1–3.6 倍**；同时 GPU 只有 5.9–25.8 ms/帧（预算 33.3 ms），**不是 GPU 瓶颈**。
3. **W92-94 是最典型的「进大地图」形状**：ops/帧掉到 **116**（几乎不画东西＝加载画面），单帧最大 **1562 ms**，而着色器 90 ms、管线 4.2 ms。**这一笔 97.4% 在引擎所有计数器之外**——与此前「4.5–4.8 s 冷启动巨帧有约 133 ms/帧花在引擎计数器之外」的结论一致，指向访客自己的场景/资源装载。
4. 启动簇（W1，4690 ms 巨帧）同样只有 0.9% 落在图形路径的编译工作上。

> **重要口径**：这四段在时间上**互相重叠**（提交路径的 CPU 时间与 GPU 等待、与访客工作都重叠），**不可相加**。因此给出的是每一段的实测值，以及「图形路径自己占超出时间多少」＝(着色器＋管线创建)/超出时间。


## 4. Q2：同一会话内第二次进入大地图是否仍然卡

### 4.1 本次会话没有「第二次进入同一场景」

证据（都来自同一份日志）：

1. **着色器侧**：491 次着色器载入对应 **491 个互不相同的 identity**，` + "`reused=0`" + `，**没有任何 identity 出现第二次**。引擎的 Shader 对象按 key 缓存在 ` + "`shaders`" + ` 表里，所以「同一场景第二次进入」本来就不该再有新的着色器载入；反过来，若第二次进入带来了同样的着色器而仍被重编，就会看到重复 identity——**没有**。
2. **场景指纹侧**：每帧 ops 数按窗口的序列是 117→157（W1–19）｜116/481/1294（W20–22）｜263/533/766（W25–27）｜725/1024/1189（W36–38）｜1104–1277（W39–71）｜1169/1674/1223/1266（W84–87）｜705/116/346（W92–94）｜334–338（W94–126）。**8 段，没有一段重复**，也就是说这次会话里每个场景只进过一次。
3. **管线侧**：W20-21 建了 57 根（warm_hits 9），W84-87 建了 104 根（warm_hits 0，79 个新 program）。这些是**新场景内容**，不是重复进入的重建。

### 4.2 对「A 类落盘缺陷导致每次进大地图都重建管线」的判定

**本次数据不能判定，既未证实也未证伪。** 两条理由：

- A 类缺陷的机制是「学到的管线配方记进内存却从不落盘，**下次启动**全部重建」。**跨启动**才是它的作用域；**同一会话内**管线本来就在内存里（` + "`pipeline_objects`" + ` 按 key 命中走 ` + "`pipeline_counts.hits`" + `），不会重复建。所以「每次进大地图都重建管线」这个说法，跨启动与同会话必须分开验证。
- 这次会话没有第二次进入同一场景，连可比的对象都没有。

**可在设备上判定的口径（1.0.7 实测值作对照）**：1.0.7 在最重的切换簇 W84-87 上 ` + "`created=104`" + `、` + "`warm_hits=0`" + `。若缺陷仍在，第二次启动后首次进大地图应当仍然是 ` + "`created≈100+`" + `、` + "`warm_hits≈0`" + `；若 A 类修复生效（warm list 自己节流落盘 + 配方作为 seed 随包分发），则应当是 ` + "`created≤10`" + `、` + "`warm_hits≥90`" + `。这写进 §7 的 E2。

## 5. Q3：城镇内 / 副本内为什么流畅

### 5.1 日志能不能区分场景：不能

- 全文的日志标签只有引擎自身的分类（` + "`[engine]`" + ` ` + "`[nvn]`" + ` ` + "`[hle]`" + ` ` + "`[audio]`" + ` ` + "`[crt]`" + ` ` + "`[page-port-policy]`" + ` ` + "`[ctor-*]`" + ` ` + "`[multiwait]`" + ` ` + "`[movie]`" + ` …），**没有任何场景/地图/关卡标识**。
- 唯一像「场景资源」的事件（` + "`nvnMemoryPoolInitialize`" + ` / ` + "`Finalize`" + ` / ` + "`nvnTexturePoolInitialize`" + `）共 51 条，**全部发生在第一个 PERF 窗口之前**（日志行 29122–43000，帧 1 之前），即启动期，**不能当场景切换信号**。
- 访客侧没有任何场景回调可挂（我们不能改游戏本体）。

### 5.2 日志能说什么

- 会话最后一段 **W94–126（1980 帧 / 66.0 s）完全平稳**：超出 0 ms/帧、着色器 0、管线创建 0、ops 稳定 334–338/帧。只要这一段是测试者待着的那个场景，它就是「流畅」的；会话里**所有**卡顿都落在 ops/帧突变处＝场景边界。
- 反过来说，现在无法证明「城镇/副本没有卡顿」这件事本身，因为无法把某段认成城镇。

### 5.3 补测方案

用新增的场景标记把「进入哪个场景」记进日志，再跑同一条路线，就能同时得到：城镇/副本/大地图各自的切换成本、大地图的首/次进入对比，以及「其它」那一段到底是谁在做。清单见 §8。

3. **访客侧装载无法在宿主侧优化**：「其它」那一段在游戏线程的访客代码里，我们的写权够不到；宿主侧能做的只有持久化管线/着色器（E2/E4）。
4. **标记文件 mtime 粒度**：部分文件系统只存秒级 mtime；两次写同一标签必须间隔 ≥ 1.1 s，否则会被算成一次进入。
5. **测量版不是基线版**：带标记时每帧多一次 ` + "`stat()`" + `，基线对比必须用同一构建并把标记关掉（标记文件删掉即回到基线行为）。
