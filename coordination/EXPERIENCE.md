## L-001 着色器改写前，先证明「这个 key 画的是谁」（2026-11-14）

**现象**：提交 `93ebe66` 对着色器 key `062df44b75d37d76` 剥掉 `gl_FragDepth`，
作者注释说它是「terrain shader」。探针实测：**这个 key 在场景里画的只有主角**。
结果主角身上长出黑色横条纹。

**错在哪**：用「注释/提交信息里的语义」代替「运行时证据里的实际使用者」。
一个 key 写错，整条改动就打在错误的物体上，而且症状出现在**另一个子系统**
（这里表现为角色渲染缺陷，完全不像「地面闪烁修复」会引发的问题）。

**正确做法**：改任何按 key 定位的着色器前，先跑一次
`gfx-codex-probe=R` → `capture.txt` 的 `PROBE_GROUP` 行给出每组 draw 的 `vs`/`fs` key，
确认该 key 的实际使用者是谁，再决定改不改。必要时看 `PROBE_DRAW` 的 draw 列表与实例数。

**出处**：`coordination/results/RG477M-FLICKER-LEFTGROUND-20261113.md` §16、§17；
修复提交 `4fc1fd7`。

## L-002 「这行是冗余的」必须用数据流证明，不能凭注释（2026-11-14）

**现象**：`93ebe66` 的前提是「地形着色器把 `gl_FragCoord.z` 存进 `gl_FragDepth`，所以这次赋值冗余」。
实测该 fs **从不对 `gl_FragCoord` 做过任何 `OpLoad`**（只有声明，没有读取），
它的 `gl_FragDepth` 存的是自己算出来的深度 ⇒ **剥离不是 no-op**，是语义改变。

**正确做法**：凡是要「删掉一次写入」的改动，先在 SPIR-V 层面证明
**被写的值 == 硬件本来会写的值**。落地方式：`xbg_spirv_reads_fragcoord()`
（该 fs 是否真的从 `gl_FragCoord` 变量加载过值）——只有「真的读了」才允许剥离。
主机契约测试：`tests/device/test_frag_depth_strip.cpp`。

**出处**：同上 §16.2、§17.3。

## L-003 整行被剔除 = 水平黑条带 ⇒ 先查深度语义，别先怀疑纹理（2026-11-14）

**现象**：主角身上的「黑色横条纹」一度被怀疑成贴图解码、合成层、抖动、屏幕录制混叠。

**破案特征（可直接复用）**：探针 color0 里主角被画成 **1px 高的水平扫描线**，
行与行之间整行是 `(0,0,0,0)`（3876 个像素只有 **1 种**取值）⇒ 这些像素**从未被写过**
⇒ 不是「画成了黑色」，而是**被深度测试整行剔除**，露出从未绘制的 clear 色。

**可复用模型**：深度语义一旦被改动，LEQUAL 比较会在「深度差函数的等值线」上翻转；
等值线落在竖立的角色身上，就是**一条条水平带**。
所以：**整行同色 + 物体空间 + 时间稳定 ⇒ 深度问题**，不是纹理问题。

**做法**：先看被剔除区域是不是「从未被写过」（取值只有 0），再看深度附件与深度测试状态，
最后才回查贴图。

**出处**：同上 §17.1、§17.2。

## L-004 A/B 归因模板：一个布尔开关 + 同机位 2×2 + 引擎侧数字（2026-11-14）

**现象**：根因定位到「某个改写」之后，必须证明它**就是**本次症状的成因。

**正确做法**：
1. 加一个**运行时标记**（读一次、启动时生效）把该路径切成 on/off，
   **不要为了 A/B 改代码编译两次**（构建 17 秒，但改代码会引入别的变量）。
2. **同机位、同存档位置、同一个 APK**（只差一个布尔；把 so 的字节差与 so 大小差记下来当证据）。
3. **两臂都要有引擎侧可量化数字**，不能只靠肉眼。本轮用的指标：
   color0 全分辨率 ROI 内「整行纯黑 ↔ 邻行有内容」的**交替行游程** ⇒ A 臂 8 行对、B 臂 0 行对。
4. 肉眼是主判据（用户在场时由用户确认），agent 负责量化佐证与机制解释；
   **一轮只问一个具体问题**，别让人反复描述同一现象。

**出处**：同上 §17.1；本轮标记见下节。

## L-005 运行时标记与探针的预算/一次性语义（2026-11-14）

- `gfx-codex-probe=R`：**每进程只跑一次**。写标记不会重新武装 ⇒ A/B 的第二臂必须**重启进程**。
  一次 9 帧抓取约 **210MB**（单帧 ~23MB），两臂就是半 GB，收尾要删。
- `gfx-live-ubtrace` / `gfx-live-framedump`：**读后即删**；抓取窗口只有几秒，
  **第一次拉可能早于文件生成**，要拉第二次。
- 标记是**一次性**的：A/B 结束后必须改名归档（`.stale*` / `.used*`），否则下一轮带假状态。
- 标记文件的读取时机决定要不要重启：着色器加载期的开关 ⇒ 必须重启；
  逐帧路径的开关（如 `gfx-live-off`）⇒ 不重启即可切。

**出处**：同上 §16.5、§17.1。

## L-006 删除的两类权限陷阱（2026-11-14）

- **本地删除**：`rm -rf` 被权限门**静默拦截**（返回 0，文件还在）⇒ 用 `find <path> -depth -delete`。
- **设备 app 属主文件**：`adb shell rm` 删不掉（Permission denied 刷屏）
  ⇒ `run-as org.ffrs.gamewindow sh -c 'find <dir> -depth -delete'`。
  设备上探针残留一次 A/B 可达 **4.7GB**；删完 `/sdcard` 可用空间从 10G 回到 15G。

**出处**：本轮设备清理（§17.5 后）。

## 2026-11-14 Codex 复核修订

- L-002 中“读取 FragCoord 即可剥离深度”的做法已撤回。真实 `062df44b75d37d76` 经 `OpAccessChain` 读取内建值，最终 `FragDepth` 经 `FMin` 等运算产生。存在读取无法证明输出与光栅深度相等。当前普通路径完整保留游戏深度，诊断开关 `gfx-terrain-depth=1` 仍为显式实验用途。证据见水都报告 §19 及提交 `1950d52`。
- 上表 `gfx-terrain-depth` 缺省含义已更新为保留原始深度。旧“auto”说明仅描述历史版本。
- 旧 `FLAME_DR` 聚合相同无法排除同 shader 子 draw 的顺序、被跳过的绘制、纯深度绘制或 GPU 间接实例变化。它在实际发出绘制前采集，并将同键绘制合并。旧 uniform trace 在 descriptor-build 路径且只哈希前 4KiB，也无法排除 memo 命中和实际 GPU 输入变化。
- 当前 `R` 路径的 `window=24` 未递减，实际由 `repeat_captures<32` 限制窗口。应按实际文件、帧号与 END 记录核对预算，旧“固定9帧”描述已过时。不要为再次取证删除尚未归档的文件。
- 在固定 `90831749` APK、PID28827 的水都场景已采集90帧。左地面具有亮度与锐度反相关的跳变。present55574 的逐 pass 证据定位到 `VS431a6183c3565f66 / FS6e2d000b284e669c` 写入 RGBA16F 透明层，`CSf55cfedfb74f811a` 随后合成。单帧贡献不能单独证明时间闪烁的成因。

### L-029 缓存槽位扩容前，先量「回退次数」（2026-11-22）

**现象**：Codex 的 Round 10 WIP 计划把 descriptor 的 memo front 与 pipe_memo 从 256 扩到 1024 槽，
理由是「命中率高、扩容能减少冲突」。直觉上像是个稳赚的改动。

**实测**：兵工厂场景 front 直接命中 384.8/帧，回退到 unordered_map 查找的次数只有
`memo_hits(505.8) - memo_front(384.8) = 121 次/帧`；pipe_memo 命中率已 95.9%（hits 391.3 / misses 16.8），
最多再省 17 次 map 查找。按整 key（数十个 word）哈希一次 0.2–0.4 µs 估算，
两项合计省不到 **0.02 ms/帧**，而该场景 submit CPU 是 **33 ms**——收益占 0.06%，量不出来。

**正确做法**：扩容前先从已有计数器算出「有多少次回退到慢路径」：
`慢路径次数 = 命中数 - 快路径命中数`。这个数乘以单次慢路径成本，才是扩容的上限收益。
上限收益小于测量噪声的改动，不要单独占用一轮构建。

**同一轮的另外两项**：FNV 增量哈希（PUSH_KEY，边构建边算 hash，hash 值与旧算法逐位相同）与
`desc_memo_reset` 的函数拆分，语义完全不变但同样只有 0.2 ms 量级，留到与主线改动合并时一起上。

**出处**：MAVIS-GPASS-ATTRIBUTION-20261122.md §5。

**真因**：`gfx-cpu-profile` 的 descriptor 明细模式会把 `descriptor_detail` 打开，而**它不会自动关**。
同一个进程里后续所有采样都带着这层插桩，所以「关掉插桩后再采」其实没关。
换成**全新进程**重测：基线包 `3f7c02e6` 与本轮 `a45430a8` 的 submit CPU 都是 31.3 ms、GPU 都是 22.33 ms、
FPS 都是 25-26 —— **逐项一致，补丁零代价**。

**规则**：
- 性能基线必须在**无插桩**的独立采样窗口里取，并且该窗口之后不再复用同一批日志。
- 插桩数据只能用于**定位热点与排序**，不能用于「改前/改后」差值结论。
- 一次性标记（`gfx-pass-live`、`gfx-cpu-profile`）读后即删，用完要确认设备上确实没有残留标记，
  否则整个会话留在慢路径上（见 L-019 的原始记录）。
- **凡是标记或开关改变过进程状态，基线必须用新进程取**，不能在同一进程里「关掉再采」。
- 跨进程比较还要控热漂移：同一进程连续跑 150 s，submit CPU 从 27.99 漂到 31.26 ms；
  两边必须同样时长的静置，否则会把热降频读成代码差异。

**出处**：MAVIS-GPASS-ATTRIBUTION-20261122.md §3、§3.1、§7。

### L-032 「少清一次缓存」等于扩大跨帧缓存寿命（L-030 之外的独立红线）

**现象**：Round 10 WIP 把 `snapshot_invalidate()` 里的 `desc_memo_reset()` 换成
`desc_memo_invalidate_local()`。两者的**唯一**语义差别是：后者**不再清 `img_cache`**。
也就是客机写了内存之后，图像缓存继续存活。

**为什么否决**：这正是 07:46 审计写死的方向——「Do not widen cross-frame image caches」，
历史 `8c009f3` 减少调用次数但帧率没降、`bd87e09` 暴露 sampler/view 身份隐患。

本项目里「多写一次清理」几乎总是比「少写一次清理」便宜。

**同族的反面例子（正确方向）**：`snapshot_invalidate` 靠遍历 map 找到要作废的 front 槽，
所以**不能**为了快而直接去掉 map —— 那会让 guest 写入后 front 仍返回旧快照。
map 在那里不是缓存，是**失效索引**，语义不可省。

### L-039 「扩大 memo 覆盖面」不等于收益：先量有多少次调用真的进了 memo（2026-11-22）

**现象**：P0 第一版把 descriptor memo 从「仅绘制」扩到「compute dispatch」，理由是兵工厂场景
每帧 348 次 descriptor 重建里有约 171 次来自 dispatch。实机 A/B（同一会话交错 ON/OFF/ON/OFF）：
descriptor 9.92–10.80 ms（ON）对 10.63–10.84 ms（OFF）—— **无差异**。

**错在哪**：把「重建次数」当成了「memo 能吃下的次数」。计数显示 compute 侧**每帧只有 1 次命中、0 次未命中**：
165 个 dispatch/帧里有 **163 个因为绑定 texel buffer（或 storage image / 写存储）被排除在 memo 之外**，
真正能进 memo 的只有约 2 个。省下 1 次重建 ≈ 13 µs ≈ 0.013 ms/帧，量不出来。
（顺带证伪了一个此前的怀疑：Honor 上 slot-local set_cache **恒 0 命中**，生产条件已与 `desc_memo_enabled`
耦合而恒被旁路，`set_key` 构造成本只有 0.01 ms/帧 ⇒「set_cache 白建」不是入口。）

**正确做法**：动缓存覆盖面之前，先把**排除原因做成计数器**（本轮加了 `desc_memo_compute_why[6]`），
量「有多少次调用真的进了缓存」。如果能进的比例很低，那么「扩大覆盖面」的上限收益 =
低比例 × 单次成本，很容易低于测量噪声（L-029 的判据）。
**排除原因比命中率更早告诉你要不要继续做**。

**出处**：MAVIS-P0-DESCRIPTOR-20261122.md §1、§4。

### L-042 开关扫描必须交错 A/B；单个 part 变好不等于整帧变快（2026-11-22）

**现象**：用 `gfx-live-set` 扫了一批既有开关（零编译）。其中 `vcache=0`（关顶点快照缓存）
让 snapshot part **稳定降 1.3–1.7 ms/帧**（5.27–5.54 → 3.80–4.43），看上去是个 1.5 ms 的现成收益。

**错在哪**：part 计数器是分桶的，**省下的时间可能只是从「snapshot 桶」挪到别的桶**，

### L-043 Android 端口的"取消/返回"是 KEYCODE_BUTTON_B(97)，不是 BACK(4)（2026-11-22）

### L-044 性能读数先验口径：三个会让人优化错地方的坑（2026-11-23）

**现象**：上一轮的 `parts_ms_per_frame` 读到 `present=16.24 ms/帧`、`descriptor=28 ms/帧`，
各部件求和 92 ms，而帧时间只有 37 ms——**自相矛盾**。重新取数后才发现读的是**游戏被切到后台**的窗口。

**三个坑**：
1. **后台节流窗口**：前台不是游戏时，系统会节流，CPU 忙从 21 ms 变成 84 ms/帧，
   `present` 会从 0.3 ms 变成 16 ms。**取任何性能数之前，先确认 `mCurrentFocus` 是游戏**。
2. **parts 是 exclusive_ns**（每帧口径、可加总），窗口正确时各部件求和 ≈ `submit_cpu_ms`；
   求和远超帧时间 = 窗口读错了，不是仪表坏了。
3. **`DESC_TIMING` 的 `descriptor_ns` 是进程启动累计**（取自 `timing.counters[...].exclusive_ns`），
   而同行的 `first/last` 只是报告窗口。**累计数不能除以窗口帧数**。

**正确做法**：拿到一行性能日志，先问三句——(1) 前台是不是游戏？(2) 这是每帧值还是窗口累计值？
(3) 各部件求和跟 `submit_cpu_ms` 对不对得上？三句都过了再解读。

**出处**：MAVIS-PERF-TEXEL-20261122.md §1。

### L-045 平板连续跑两分钟会降频 20%+，顺序测量会把漂移读成差异（2026-11-23）

**现象**：同一轮测试内 2 分钟，`submit_cpu` 从 18.8 ms 涨到 28.8 ms、fps 从 36.7 掉到 29.0（−21%）。

### L-049 给 memo 加一种新绑定前，先算"命中路径的新增成本"（2026-11-23）

**现象**：把 texel 绑定放进 descriptor memo，本以为能省掉 423 次/帧的整表重建（每次 ~20 µs），
实机 A/B 却是 **+2.49 ms/帧（更慢）**：重建只少了 103 次（−1.62 ms），
而 memo 命中路径每次都要刷新目标缓冲，1629 次/帧 × 1.69 µs = **+2.75 ms**，正好把收益吃光还倒欠。

**正确做法**：memo 化的收益要按"**命中数 × (重建成本 − 命中成本)**"算，**不是**按"少了几次重建"算；
而命中路径一旦新增"刷新/校验"动作，成本要乘以**命中次数**（本例 1629/帧，远大于重建次数 445/帧），
必须在动手前把这个乘数算清楚。新增动作要么摊到"每资源每提交一次"，要么把校验做成 O(1)。

**出处**：MAVIS-PERF-V2-TEXELPOOL-20261123.md §4。

### L-050 memo 化一个绑定的真正瓶颈可能是"键的稳定性"，不是绑定本身（2026-11-23）

**现象**：解除 texel 的 memo 排除后，423 个 draw 变成可 memo，但只有约 103 个真能命中，
其余 96.8 次/帧是 memo 未命中。追下去发现 `keydiff tex=154/帧`：**很多 draw 的纹理句柄每帧在变**，
键一变必然 miss。也就是说：**即使把绑定的生命周期处理完美，键不稳照样命中不了**。

**正确做法**：评估 memo 化收益前，先量键的稳定性（键里哪些分量每帧在变、变了多少次）。
键里带"每帧会变的代次/句柄"时，先问一句：**这份稳定性是不是由 verify 已经覆盖的语义保证的？**
若 verify（注册版本 + serial + 存活身份）已经能判等价，键里就不必再带易变分量。

**出处**：MAVIS-PERF-V2-TEXELPOOL-20261123.md §4、§5。

### L-051 池化/共享缓冲前先算内存账与命中天花板（2026-11-23）

**现象**：每 slot 4 MB 的 texel 目标缓冲池 × 16 slot = 64 MB 常驻，且 4 MB 上限导致 84–94 次/帧

**正确做法**：池化的三个账要一起算：**内存**（每 slot × slot 数，或改共享池）、

**出处**：MAVIS-PERF-V2-TEXELPOOL-20261123.md §4、§5。

### L-052 keydiff 普查比的是"相邻两次同 shader 的键"，不是"memo 未命中的键"（2026-11-23）

**现象**：上一轮报告里 `keydiff tex=154/帧` 被读成"很多 draw 的纹理句柄每帧在变 ⇒ memo 键不稳 ⇒ 必然 miss"，
于是把"memo 键的 tex 分量换成稳定纹理 id"列为下一版第一枪。
实机把它做成运行时开关做交错 A/B，结果 **memo_hits 405.1 vs 405.0、重建数一模一样、帧率零变化**。

**真相**：`keydiff` 普查比较的是"**同一 shader 相邻两次的键**"（诊断"这次绑定和上次哪里不一样"），
**不是**"这次查找与 memo 里存的那个键差在哪"（后者是 `memo_misses` / `vwhy_*` 的职责）。
两者含义不同，不能拿前者推断未命中的原因。

**正确做法**：判断 memo 为什么未命中，只看 `memo_misses` / `memo_front` / `why=texel…` / `vwhy=…`
这几组计数；`keydiff` 只用于回答"这两次绑定内容变了没有"。
**任何基于 keydiff 的优化设想，先做一次运行时开关 A/B 证伪，再写进下一版计划。**

**出处**：MAVIS-PERF-V2-TEXELPOOL-20261123.md §8。


### L-053 探针标记文件的字段数不对，fscanf 会静默跳过而不是报错（2026-11-23）

**现象**：`gfx-cpu-profile` 标记文件确认在设备上，引擎却一个 `NVN DESC_TIMING` 都没打印，
上一轮据此判成"探针没装上、根因未定位"，白找了一轮。

**真相**：引擎读这个标记用 `fscanf(m,"%llu %u %u",&s,&c,&detail)`，**需要三个字段**（start / count / detail）。
只写一个字段时 `fscanf` 返回 1，而代码里的条件是 `>=2`，于是**整段探针被静默跳过**：不报错、不打日志、不降级。
正确写法：`printf '0 30 1' > $F/gfx-cpu-profile`（start=0，count=30 帧，detail=1）。

**正确做法**：写标记文件前，先读引擎那一侧的 `fscanf` 格式串，按它给的字段数写；
写完确认文件内容与字段数一致，再看引擎有没有真的打印探针输出。
**"标记文件存在"不等于"探针生效"**——静默跳过是无声的。

**出处**：MAVIS-PERF-V3-TEXELKEY-20261123.md §2。

**症状**：V3 探针（arm7）在读档加载阶段必崩，arm0/arm4/arm5 全过；
崩溃点查不到日志（设备不落 tombstone，见 L-065），只剩 `Dying app ... isFromBinderDied:true`。

**分臂二分把它锁到单个开关**：`texelkey=1` 必崩，`texelkey=0`（不论 pool/fast 怎么配）都不崩。

**代码复核命中**（V3 新增的诊断计数器 `texel_key_census`）：

```cpp
auto it=texel_key_sites.find(site);
if(it!=texel_key_sites.end()&&it->second.frame+1==fr){...}
it->second.id=id;it->second.frame=fr;   // ← it 可能 == end()
```

最后两行无条件执行。站点第一次出现时 `find()` 返回 `end()`，
**对 `end()` 迭代器解引用写入是未定义行为**——被写坏的是哈希表自己的内部结构，
所以崩溃点与出错点相隔很远（几秒后），而且日志里什么都看不到。

**修法**：`operator[]` 插入站点；用 `frame=0` 表示"没见过"，不参与相邻帧比较。

**通用教训（三条，同族）**：
1. `find()` 之后**无条件**写 `it->second` 是最常见的 UB 写法，编译器不报错、sanitizer 才报；
2. **UB 的现场和崩溃现场可以相隔很远**，而且往往只在一组开关组合下才触发——
   所以定位手段应该是**分臂二分**（把开关空间切小），不是读日志；
3. 诊断/计数代码**也会变成生产事故**：它和被测路径共享同一个调用点，
   一个只读不改的计数器照样能打崩整个进程。

**出处**：MAVIS-PERF-V3-TEXELKEY-20261123.md §10.6。
### L-067 帧率的 1.75× 摆动来自主线程跨核迁移，不是代码路径变慢（2026-11-23）

**现象**：同一个位置（draws 恒为 602）、同一套代码，帧率会在**进入位置后约 20 秒内从 40+ 掉到 26~30 并保持**。
两种测量方法（进程间定臂、进程内 6 秒交错切臂）都看到这个掉速点，**两臂在同一个窗口序号同步发生**。

**判读证据**：掉速时**所有子域同比例放大**——descriptor 5.21→9.13、draw 1.61→3.17、dispatch 1.09→2.15 ms。
一条代码路径变慢不会让所有子域等比放大；**这是"CPU 整体变慢"的特征**。

**实测佐证**：
- `/proc/<pid>/task/<tid>/stat` 第 39 字段：游戏主线程 `ffrs.gamewindow` **在 cpu3~6 之间来回迁移**；
- `/sys/devices/system/cpu/cpuN/cpufreq/scaling_cur_freq`：cpu0 ~1.0~1.7 GHz、cpu3 2.7 GHz、cpu7 0.63~3.0 GHz 跳变；
- `dumpsys thermalservice`：Thermal Status = 0、电池 21 °C ⇒ **不是热降频，是调度**。

**代码现状**：`xbg_game.cpp:163` 只有 `setpriority(PRIO_PROCESS,0,-10)`，**没有任何绑核**。

**两条方法论**：
1. **先看是不是"所有路径等比变化"**——是就不是某条路径的锅，去查调度/频率；
2. **进程间对比会被设备状态污染**（本轮同一位置跨进程差 ±3.5 fps），
   帧率结论必须用**进程内时间交错**（两臂放在同一进程、同一时刻）。

**出处**：MAVIS-PERF-V3-TEXELKEY-20261123.md §10.11。
### L-068 掉速真因：渲染线程被系统挪出超大核（掩码 0xFF -> 0x7F）（2026-11-23）

**现象**：同一位置（draws=602）、同一套代码，进入重场景后帧率从 40+ 掉到 26~33 并保持；
所有子域等比放大 ~1.6x，工作量（ops/draws）完全不变。

**根因**：图形翻译线程 `dm-gfx` 的 `Cpus_allowed_list` 是 **0-6**，
而同一进程其余 40+ 线程全是 **0-7**——只有它被排除在 Cortex-X4（cpu7, 3.014 GHz）之外，
只能在 Cortex-A720（cpu3-6, 2.803 GHz）上跑。X4 与 A720 的 IPC+频率差正好解释 1.6x 的每帧 CPU 时间。
系统会在进入重场景后把掩码从 0xFF 收窄成 0x7F，实测发生在 present 61 -> 4681 之间（约 10~25 秒内）。

**修法**：图形线程启动时按 `cpuinfo_max_freq` 识别最快核并 `sched_setaffinity` 独占它，
每帧复查一次掩码、被收窄就抢回。实机：33.8 -> 46.6 fps（+38%），submit_cpu 25.2 -> 15.7 ms。

**通用教训**：
1. **"所有子域等比变慢"= 线程被换了运行环境**，不是代码路径变慢；
2. 查掉速真因的顺序是：**先线程级归属**（谁吃满单核）-> **再核掩码**（Cpus_allowed_list）
   -> **再频率/温度**（cpufreq / thermalservice）。本轮先查频率和温度，全部正常，才被迫往线程方向挖；
3. 掩码是**逐线程**的，不能用 cgroup 或整机视角看——同进程其它线程的掩码会掩盖问题。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 2.3~2.4 节。

### L-069 撤回 L-067 的"主线程跨核迁移"归因（2026-11-23）

L-067 写的是"游戏主线程 `ffrs.gamewindow` 在 cpu3~6 之间来回迁移"。**该具体归因在此撤回。**
线程级采样证明：主线程只占约 5% CPU（10 秒 +43~50 jiffies），
真正吃满单核的是 `dm-gfx`（+811~918 jiffies/10 秒，约 90~100%）。
主线程的迁移与帧率掉速没有因果关系；掉速来自 `dm-gfx` 的核掩码被收窄（见 L-068）。

**教训**：把"某个线程在迁移"当成因果前，先确认**那个线程是不是热点**；

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 2.1 节与第 6 节。

### L-070 客机导入是严格白名单 ⇒ 客机改不了本进程的核掩码（2026-11-23）

- `src/runtime/hle/nso/nso_call.c:resolve_import` 只放行一个**固定白名单**

### L-071 live-set 字符串开关必须真的把值写进去（2026-11-23）

新增 live-set 开关 `gfxaffinity=prime|big|off` 时，采样脚本里写成

### L-073 基线臂必须显式指定核，"系统放置"臂不可复现（2026-11-23）

想拿"不绑核"当基线，实测不可行：系统会在进入重场景后自行把掩码改成 0x7F，
所以"不干预"臂在热态下**等价于绑到 A720 簇**，而且是**不可复现**的（什么时候收窄受设备状态影响）。
可复现的做法是：基线臂显式绑到 big cluster（掩码 0x78），处理臂显式绑到 prime（0x80），
两臂在同一进程内交错。这样基线与处理只差"哪个核"这一个变量。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 4 节。

### L-074 绑核要加异构闸门：同构设备不绑（2026-11-23）

绑超大核在异构 SoC 上是纯收益，但同构 SoC（所有核同频，例如最终目标 RG477M 这类）上
绑一个核没有任何收益，却会让该核不能再服务系统其它工作。
做法：读 `cpuinfo_max_freq` 分档，**只有存在两个不同频率档（prime > second）才绑**，

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 3 节第 2 条与第 8 节。

### L-076 场景覆盖复测要分三档采样，不能只测静止 (2026-11-23)

"这个场景够不够 40 Hz"不能只测静止帧。同一个场景至少要分三档：
**静止 / 特效峰值 / 移动**，三者差距可以很大。
实测月夜火场：静止 50.2~56.6 fps，**攻击特效生效的那几秒掉到 41.0~43.4 fps**
（submit_cpu 14.8→19.1、gpu 13.7→16.8），走出火焰区的走廊又是 59.5~60.0 fps。
只测静止会得出"这场景很宽裕"的错误结论，真实的最紧一档是特效峰值。
做法：静止 20 轮 × 6 s 连续采样 → 连续触发特效并每秒采样 → 移动中采样，三档都记。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 12.1 节。
