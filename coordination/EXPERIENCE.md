## L-001 着色器改写前，先证明「这个 key 画的是谁」（2026-11-14）

**现象**：提交 `93ebe66` 对着色器 key `062df44b75d37d76` 剥掉 `gl_FragDepth`，
作者注释说它是「terrain shader」。探针实测：**这个 key 在场景里画的只有主角**。
结果主角身上长出黑色横条纹。

**错在哪**：用「注释/提交信息里的语义」代替「运行时证据里的实际使用者」。
一个 key 写错，整条改动就打在错误的物体上，而且症状出现在**另一个子系统**
（这里表现为角色渲染缺陷，完全不像「地面闪烁修复」会引发的问题）。

**正确做法**：改任何按 key 定位的着色器前，先跑一次
`gfx-codex-probe=R` → `capture.txt` 的 `PROBE_GROUP` 行给出每组 draw 的 `vs`/`fs` key，
确认该 key 的实际使用者是谁，再决定改不改。必要时看 `PROBE_DRAW` 的 draw 列表与实例数。

**出处**：`coordination/results/RG477M-FLICKER-LEFTGROUND-20261113.md` §16、§17；
修复提交 `4fc1fd7`。

## L-002 「这行是冗余的」必须用数据流证明，不能凭注释（2026-11-14）

**现象**：`93ebe66` 的前提是「地形着色器把 `gl_FragCoord.z` 存进 `gl_FragDepth`，所以这次赋值冗余」。
实测该 fs **从不对 `gl_FragCoord` 做过任何 `OpLoad`**（只有声明，没有读取），
它的 `gl_FragDepth` 存的是自己算出来的深度 ⇒ **剥离不是 no-op**，是语义改变。

**正确做法**：凡是要「删掉一次写入」的改动，先在 SPIR-V 层面证明
**被写的值 == 硬件本来会写的值**。落地方式：`xbg_spirv_reads_fragcoord()`
（该 fs 是否真的从 `gl_FragCoord` 变量加载过值）——只有「真的读了」才允许剥离。
主机契约测试：`tests/device/test_frag_depth_strip.cpp`。

**出处**：同上 §16.2、§17.3。

## L-003 整行被剔除 = 水平黑条带 ⇒ 先查深度语义，别先怀疑纹理（2026-11-14）

**现象**：主角身上的「黑色横条纹」一度被怀疑成贴图解码、合成层、抖动、屏幕录制混叠。

**破案特征（可直接复用）**：探针 color0 里主角被画成 **1px 高的水平扫描线**，
行与行之间整行是 `(0,0,0,0)`（3876 个像素只有 **1 种**取值）⇒ 这些像素**从未被写过**
⇒ 不是「画成了黑色」，而是**被深度测试整行剔除**，露出从未绘制的 clear 色。

**可复用模型**：深度语义一旦被改动，LEQUAL 比较会在「深度差函数的等值线」上翻转；
等值线落在竖立的角色身上，就是**一条条水平带**。
所以：**整行同色 + 物体空间 + 时间稳定 ⇒ 深度问题**，不是纹理问题。

**做法**：先看被剔除区域是不是「从未被写过」（取值只有 0），再看深度附件与深度测试状态，
最后才回查贴图。

**出处**：同上 §17.1、§17.2。

## L-004 A/B 归因模板：一个布尔开关 + 同机位 2×2 + 引擎侧数字（2026-11-14）

**现象**：根因定位到「某个改写」之后，必须证明它**就是**本次症状的成因。

**正确做法**：
1. 加一个**运行时标记**（读一次、启动时生效）把该路径切成 on/off，
   **不要为了 A/B 改代码编译两次**（构建 17 秒，但改代码会引入别的变量）。
2. **同机位、同存档位置、同一个 APK**（只差一个布尔；把 so 的字节差与 so 大小差记下来当证据）。
3. **两臂都要有引擎侧可量化数字**，不能只靠肉眼。本轮用的指标：
   color0 全分辨率 ROI 内「整行纯黑 ↔ 邻行有内容」的**交替行游程** ⇒ A 臂 8 行对、B 臂 0 行对。
4. 肉眼是主判据（用户在场时由用户确认），agent 负责量化佐证与机制解释；
   **一轮只问一个具体问题**，别让人反复描述同一现象。

**出处**：同上 §17.1；本轮标记见下节。

## L-005 运行时标记与探针的预算/一次性语义（2026-11-14）

- `gfx-codex-probe=R`：**每进程只跑一次**。写标记不会重新武装 ⇒ A/B 的第二臂必须**重启进程**。
  一次 9 帧抓取约 **210MB**（单帧 ~23MB），两臂就是半 GB，收尾要删。
- `gfx-live-ubtrace` / `gfx-live-framedump`：**读后即删**；抓取窗口只有几秒，
  **第一次拉可能早于文件生成**，要拉第二次。
- 标记是**一次性**的：A/B 结束后必须改名归档（`.stale*` / `.used*`），否则下一轮带假状态。
- 标记文件的读取时机决定要不要重启：着色器加载期的开关 ⇒ 必须重启；
  逐帧路径的开关（如 `gfx-live-off`）⇒ 不重启即可切。

**出处**：同上 §16.5、§17.1。

## L-006 删除的两类权限陷阱（2026-11-14）

- **本地删除**：`rm -rf` 被权限门**静默拦截**（返回 0，文件还在）⇒ 用 `find <path> -depth -delete`。
- **设备 app 属主文件**：`adb shell rm` 删不掉（Permission denied 刷屏）
  ⇒ `run-as org.ffrs.gamewindow sh -c 'find <dir> -depth -delete'`。
  设备上探针残留一次 A/B 可达 **4.7GB**；删完 `/sdcard` 可用空间从 10G 回到 15G。

**出处**：本轮设备清理（§17.5 后）。

## 2026-11-14 Codex 复核修订

- L-002 中“读取 FragCoord 即可剥离深度”的做法已撤回。真实 `062df44b75d37d76` 经 `OpAccessChain` 读取内建值，最终 `FragDepth` 经 `FMin` 等运算产生。存在读取无法证明输出与光栅深度相等。当前普通路径完整保留游戏深度，诊断开关 `gfx-terrain-depth=1` 仍为显式实验用途。证据见水都报告 §19 及提交 `1950d52`。
- 上表 `gfx-terrain-depth` 缺省含义已更新为保留原始深度。旧“auto”说明仅描述历史版本。
- 旧 `FLAME_DR` 聚合相同无法排除同 shader 子 draw 的顺序、被跳过的绘制、纯深度绘制或 GPU 间接实例变化。它在实际发出绘制前采集，并将同键绘制合并。旧 uniform trace 在 descriptor-build 路径且只哈希前 4KiB，也无法排除 memo 命中和实际 GPU 输入变化。
- 当前 `R` 路径的 `window=24` 未递减，实际由 `repeat_captures<32` 限制窗口。应按实际文件、帧号与 END 记录核对预算，旧“固定9帧”描述已过时。不要为再次取证删除尚未归档的文件。
- 在固定 `90831749` APK、PID28827 的水都场景已采集90帧。左地面具有亮度与锐度反相关的跳变。present55574 的逐 pass 证据定位到 `VS431a6183c3565f66 / FS6e2d000b284e669c` 写入 RGBA16F 透明层，`CSf55cfedfb74f811a` 随后合成。单帧贡献不能单独证明时间闪烁的成因。

### L-029 缓存槽位扩容前，先量「回退次数」（2026-11-22）

**现象**：Codex 的 Round 10 WIP 计划把 descriptor 的 memo front 与 pipe_memo 从 256 扩到 1024 槽，
理由是「命中率高、扩容能减少冲突」。直觉上像是个稳赚的改动。

**实测**：兵工厂场景 front 直接命中 384.8/帧，回退到 unordered_map 查找的次数只有
`memo_hits(505.8) - memo_front(384.8) = 121 次/帧`；pipe_memo 命中率已 95.9%（hits 391.3 / misses 16.8），
最多再省 17 次 map 查找。按整 key（数十个 word）哈希一次 0.2–0.4 µs 估算，
两项合计省不到 **0.02 ms/帧**，而该场景 submit CPU 是 **33 ms**——收益占 0.06%，量不出来。

**正确做法**：扩容前先从已有计数器算出「有多少次回退到慢路径」：
`慢路径次数 = 命中数 - 快路径命中数`。这个数乘以单次慢路径成本，才是扩容的上限收益。
上限收益小于测量噪声的改动，不要单独占用一轮构建。

**同一轮的另外两项**：FNV 增量哈希（PUSH_KEY，边构建边算 hash，hash 值与旧算法逐位相同）与
`desc_memo_reset` 的函数拆分，语义完全不变但同样只有 0.2 ms 量级，留到与主线改动合并时一起上。

**出处**：MAVIS-GPASS-ATTRIBUTION-20261122.md §5。

**真因**：`gfx-cpu-profile` 的 descriptor 明细模式会把 `descriptor_detail` 打开，而**它不会自动关**。
同一个进程里后续所有采样都带着这层插桩，所以「关掉插桩后再采」其实没关。
换成**全新进程**重测：基线包 `3f7c02e6` 与本轮 `a45430a8` 的 submit CPU 都是 31.3 ms、GPU 都是 22.33 ms、
FPS 都是 25-26 —— **逐项一致，补丁零代价**。

**规则**：
- 性能基线必须在**无插桩**的独立采样窗口里取，并且该窗口之后不再复用同一批日志。
- 插桩数据只能用于**定位热点与排序**，不能用于「改前/改后」差值结论。
- 一次性标记（`gfx-pass-live`、`gfx-cpu-profile`）读后即删，用完要确认设备上确实没有残留标记，
  否则整个会话留在慢路径上（见 L-019 的原始记录）。
- **凡是标记或开关改变过进程状态，基线必须用新进程取**，不能在同一进程里「关掉再采」。
- 跨进程比较还要控热漂移：同一进程连续跑 150 s，submit CPU 从 27.99 漂到 31.26 ms；
  两边必须同样时长的静置，否则会把热降频读成代码差异。

**出处**：MAVIS-GPASS-ATTRIBUTION-20261122.md §3、§3.1、§7。

### L-032 「少清一次缓存」等于扩大跨帧缓存寿命（L-030 之外的独立红线）

**现象**：Round 10 WIP 把 `snapshot_invalidate()` 里的 `desc_memo_reset()` 换成
`desc_memo_invalidate_local()`。两者的**唯一**语义差别是：后者**不再清 `img_cache`**。
也就是客机写了内存之后，图像缓存继续存活。

**为什么否决**：这正是 07:46 审计写死的方向——「Do not widen cross-frame image caches」，
历史 `8c009f3` 减少调用次数但帧率没降、`bd87e09` 暴露 sampler/view 身份隐患。

本项目里「多写一次清理」几乎总是比「少写一次清理」便宜。

**同族的反面例子（正确方向）**：`snapshot_invalidate` 靠遍历 map 找到要作废的 front 槽，
所以**不能**为了快而直接去掉 map —— 那会让 guest 写入后 front 仍返回旧快照。
map 在那里不是缓存，是**失效索引**，语义不可省。

### L-039 「扩大 memo 覆盖面」不等于收益：先量有多少次调用真的进了 memo（2026-11-22）

**现象**：P0 第一版把 descriptor memo 从「仅绘制」扩到「compute dispatch」，理由是兵工厂场景
每帧 348 次 descriptor 重建里有约 171 次来自 dispatch。实机 A/B（同一会话交错 ON/OFF/ON/OFF）：
descriptor 9.92–10.80 ms（ON）对 10.63–10.84 ms（OFF）—— **无差异**。

**错在哪**：把「重建次数」当成了「memo 能吃下的次数」。计数显示 compute 侧**每帧只有 1 次命中、0 次未命中**：
165 个 dispatch/帧里有 **163 个因为绑定 texel buffer（或 storage image / 写存储）被排除在 memo 之外**，
真正能进 memo 的只有约 2 个。省下 1 次重建 ≈ 13 µs ≈ 0.013 ms/帧，量不出来。
（顺带证伪了一个此前的怀疑：Honor 上 slot-local set_cache **恒 0 命中**，生产条件已与 `desc_memo_enabled`
耦合而恒被旁路，`set_key` 构造成本只有 0.01 ms/帧 ⇒「set_cache 白建」不是入口。）

**正确做法**：动缓存覆盖面之前，先把**排除原因做成计数器**（本轮加了 `desc_memo_compute_why[6]`），
量「有多少次调用真的进了缓存」。如果能进的比例很低，那么「扩大覆盖面」的上限收益 =
低比例 × 单次成本，很容易低于测量噪声（L-029 的判据）。
**排除原因比命中率更早告诉你要不要继续做**。

**出处**：MAVIS-P0-DESCRIPTOR-20261122.md §1、§4。

### L-042 开关扫描必须交错 A/B；单个 part 变好不等于整帧变快（2026-11-22）

**现象**：用 `gfx-live-set` 扫了一批既有开关（零编译）。其中 `vcache=0`（关顶点快照缓存）
让 snapshot part **稳定降 1.3–1.7 ms/帧**（5.27–5.54 → 3.80–4.43），看上去是个 1.5 ms 的现成收益。

**错在哪**：part 计数器是分桶的，**省下的时间可能只是从「snapshot 桶」挪到别的桶**，

### L-043 Android 端口的"取消/返回"是 KEYCODE_BUTTON_B(97)，不是 BACK(4)（2026-11-22）

### L-044 性能读数先验口径：三个会让人优化错地方的坑（2026-11-23）

**现象**：上一轮的 `parts_ms_per_frame` 读到 `present=16.24 ms/帧`、`descriptor=28 ms/帧`，
各部件求和 92 ms，而帧时间只有 37 ms——**自相矛盾**。重新取数后才发现读的是**游戏被切到后台**的窗口。

**三个坑**：
1. **后台节流窗口**：前台不是游戏时，系统会节流，CPU 忙从 21 ms 变成 84 ms/帧，
   `present` 会从 0.3 ms 变成 16 ms。**取任何性能数之前，先确认 `mCurrentFocus` 是游戏**。
2. **parts 是 exclusive_ns**（每帧口径、可加总），窗口正确时各部件求和 ≈ `submit_cpu_ms`；
   求和远超帧时间 = 窗口读错了，不是仪表坏了。
3. **`DESC_TIMING` 的 `descriptor_ns` 是进程启动累计**（取自 `timing.counters[...].exclusive_ns`），
   而同行的 `first/last` 只是报告窗口。**累计数不能除以窗口帧数**。

**正确做法**：拿到一行性能日志，先问三句——(1) 前台是不是游戏？(2) 这是每帧值还是窗口累计值？
(3) 各部件求和跟 `submit_cpu_ms` 对不对得上？三句都过了再解读。

**出处**：MAVIS-PERF-TEXEL-20261122.md §1。

### L-045 平板连续跑两分钟会降频 20%+，顺序测量会把漂移读成差异（2026-11-23）

**现象**：同一轮测试内 2 分钟，`submit_cpu` 从 18.8 ms 涨到 28.8 ms、fps 从 36.7 掉到 29.0（−21%）。

### L-049 给 memo 加一种新绑定前，先算"命中路径的新增成本"（2026-11-23）

**现象**：把 texel 绑定放进 descriptor memo，本以为能省掉 423 次/帧的整表重建（每次 ~20 µs），
实机 A/B 却是 **+2.49 ms/帧（更慢）**：重建只少了 103 次（−1.62 ms），
而 memo 命中路径每次都要刷新目标缓冲，1629 次/帧 × 1.69 µs = **+2.75 ms**，正好把收益吃光还倒欠。

**正确做法**：memo 化的收益要按"**命中数 × (重建成本 − 命中成本)**"算，**不是**按"少了几次重建"算；
而命中路径一旦新增"刷新/校验"动作，成本要乘以**命中次数**（本例 1629/帧，远大于重建次数 445/帧），
必须在动手前把这个乘数算清楚。新增动作要么摊到"每资源每提交一次"，要么把校验做成 O(1)。

**出处**：MAVIS-PERF-V2-TEXELPOOL-20261123.md §4。

### L-050 memo 化一个绑定的真正瓶颈可能是"键的稳定性"，不是绑定本身（2026-11-23）

**现象**：解除 texel 的 memo 排除后，423 个 draw 变成可 memo，但只有约 103 个真能命中，
其余 96.8 次/帧是 memo 未命中。追下去发现 `keydiff tex=154/帧`：**很多 draw 的纹理句柄每帧在变**，
键一变必然 miss。也就是说：**即使把绑定的生命周期处理完美，键不稳照样命中不了**。

**正确做法**：评估 memo 化收益前，先量键的稳定性（键里哪些分量每帧在变、变了多少次）。
键里带"每帧会变的代次/句柄"时，先问一句：**这份稳定性是不是由 verify 已经覆盖的语义保证的？**
若 verify（注册版本 + serial + 存活身份）已经能判等价，键里就不必再带易变分量。

**出处**：MAVIS-PERF-V2-TEXELPOOL-20261123.md §4、§5。

### L-051 池化/共享缓冲前先算内存账与命中天花板（2026-11-23）

**现象**：每 slot 4 MB 的 texel 目标缓冲池 × 16 slot = 64 MB 常驻，且 4 MB 上限导致 84–94 次/帧

**正确做法**：池化的三个账要一起算：**内存**（每 slot × slot 数，或改共享池）、

**出处**：MAVIS-PERF-V2-TEXELPOOL-20261123.md §4、§5。

### L-052 keydiff 普查比的是"相邻两次同 shader 的键"，不是"memo 未命中的键"（2026-11-23）

**现象**：上一轮报告里 `keydiff tex=154/帧` 被读成"很多 draw 的纹理句柄每帧在变 ⇒ memo 键不稳 ⇒ 必然 miss"，
于是把"memo 键的 tex 分量换成稳定纹理 id"列为下一版第一枪。
实机把它做成运行时开关做交错 A/B，结果 **memo_hits 405.1 vs 405.0、重建数一模一样、帧率零变化**。

**真相**：`keydiff` 普查比较的是"**同一 shader 相邻两次的键**"（诊断"这次绑定和上次哪里不一样"），
**不是**"这次查找与 memo 里存的那个键差在哪"（后者是 `memo_misses` / `vwhy_*` 的职责）。
两者含义不同，不能拿前者推断未命中的原因。

**正确做法**：判断 memo 为什么未命中，只看 `memo_misses` / `memo_front` / `why=texel…` / `vwhy=…`
这几组计数；`keydiff` 只用于回答"这两次绑定内容变了没有"。
**任何基于 keydiff 的优化设想，先做一次运行时开关 A/B 证伪，再写进下一版计划。**

**出处**：MAVIS-PERF-V2-TEXELPOOL-20261123.md §8。


### L-053 探针标记文件的字段数不对，fscanf 会静默跳过而不是报错（2026-11-23）

**现象**：`gfx-cpu-profile` 标记文件确认在设备上，引擎却一个 `NVN DESC_TIMING` 都没打印，
上一轮据此判成"探针没装上、根因未定位"，白找了一轮。

**真相**：引擎读这个标记用 `fscanf(m,"%llu %u %u",&s,&c,&detail)`，**需要三个字段**（start / count / detail）。
只写一个字段时 `fscanf` 返回 1，而代码里的条件是 `>=2`，于是**整段探针被静默跳过**：不报错、不打日志、不降级。
正确写法：`printf '0 30 1' > $F/gfx-cpu-profile`（start=0，count=30 帧，detail=1）。

**正确做法**：写标记文件前，先读引擎那一侧的 `fscanf` 格式串，按它给的字段数写；
写完确认文件内容与字段数一致，再看引擎有没有真的打印探针输出。
**"标记文件存在"不等于"探针生效"**——静默跳过是无声的。

**出处**：MAVIS-PERF-V3-TEXELKEY-20261123.md §2。

**出处**：MAVIS-PERF-V3-TEXELKEY-20261123.md §10.7。### L-066 对 unordered_map 的 end() 迭代器解引用写入 = 崩溃根因（2026-11-23）

**症状**：V3 探针（arm7）在读档加载阶段必崩，arm0/arm4/arm5 全过；
崩溃点查不到日志（设备不落 tombstone，见 L-065），只剩 `Dying app ... isFromBinderDied:true`。

**分臂二分把它锁到单个开关**：`texelkey=1` 必崩，`texelkey=0`（不论 pool/fast 怎么配）都不崩。

**代码复核命中**（V3 新增的诊断计数器 `texel_key_census`）：

```cpp
auto it=texel_key_sites.find(site);
if(it!=texel_key_sites.end()&&it->second.frame+1==fr){...}
it->second.id=id;it->second.frame=fr;   // ← it 可能 == end()
```

最后两行无条件执行。站点第一次出现时 `find()` 返回 `end()`，
**对 `end()` 迭代器解引用写入是未定义行为**——被写坏的是哈希表自己的内部结构，
所以崩溃点与出错点相隔很远（几秒后），而且日志里什么都看不到。

**修法**：`operator[]` 插入站点；用 `frame=0` 表示"没见过"，不参与相邻帧比较。

**通用教训（三条，同族）**：
1. `find()` 之后**无条件**写 `it->second` 是最常见的 UB 写法，编译器不报错、sanitizer 才报；
2. **UB 的现场和崩溃现场可以相隔很远**，而且往往只在一组开关组合下才触发——
   所以定位手段应该是**分臂二分**（把开关空间切小），不是读日志；
3. 诊断/计数代码**也会变成生产事故**：它和被测路径共享同一个调用点，
   一个只读不改的计数器照样能打崩整个进程。

**出处**：MAVIS-PERF-V3-TEXELKEY-20261123.md §10.6。
### L-067 帧率的 1.75× 摆动来自主线程跨核迁移，不是代码路径变慢（2026-11-23）

**现象**：同一个位置（draws 恒为 602）、同一套代码，帧率会在**进入位置后约 20 秒内从 40+ 掉到 26~30 并保持**。
两种测量方法（进程间定臂、进程内 6 秒交错切臂）都看到这个掉速点，**两臂在同一个窗口序号同步发生**。

**判读证据**：掉速时**所有子域同比例放大**——descriptor 5.21→9.13、draw 1.61→3.17、dispatch 1.09→2.15 ms。
一条代码路径变慢不会让所有子域等比放大；**这是"CPU 整体变慢"的特征**。

**实测佐证**：
- `/proc/<pid>/task/<tid>/stat` 第 39 字段：游戏主线程 `ffrs.gamewindow` **在 cpu3~6 之间来回迁移**；
- `/sys/devices/system/cpu/cpuN/cpufreq/scaling_cur_freq`：cpu0 ~1.0~1.7 GHz、cpu3 2.7 GHz、cpu7 0.63~3.0 GHz 跳变；
- `dumpsys thermalservice`：Thermal Status = 0、电池 21 °C ⇒ **不是热降频，是调度**。

**代码现状**：`xbg_game.cpp:163` 只有 `setpriority(PRIO_PROCESS,0,-10)`，**没有任何绑核**。

**两条方法论**：
1. **先看是不是"所有路径等比变化"**——是就不是某条路径的锅，去查调度/频率；
2. **进程间对比会被设备状态污染**（本轮同一位置跨进程差 ±3.5 fps），
   帧率结论必须用**进程内时间交错**（两臂放在同一进程、同一时刻）。

**出处**：MAVIS-PERF-V3-TEXELKEY-20261123.md §10.11。
### L-068 掉速真因：渲染线程被系统挪出超大核（掩码 0xFF -> 0x7F）（2026-11-23）

**现象**：同一位置（draws=602）、同一套代码，进入重场景后帧率从 40+ 掉到 26~33 并保持；
所有子域等比放大 ~1.6x，工作量（ops/draws）完全不变。

**根因**：图形翻译线程 `dm-gfx` 的 `Cpus_allowed_list` 是 **0-6**，
而同一进程其余 40+ 线程全是 **0-7**——只有它被排除在 Cortex-X4（cpu7, 3.014 GHz）之外，
只能在 Cortex-A720（cpu3-6, 2.803 GHz）上跑。X4 与 A720 的 IPC+频率差正好解释 1.6x 的每帧 CPU 时间。
系统会在进入重场景后把掩码从 0xFF 收窄成 0x7F，实测发生在 present 61 -> 4681 之间（约 10~25 秒内）。

**修法**：图形线程启动时按 `cpuinfo_max_freq` 识别最快核并 `sched_setaffinity` 独占它，
每帧复查一次掩码、被收窄就抢回。实机：33.8 -> 46.6 fps（+38%），submit_cpu 25.2 -> 15.7 ms。

**通用教训**：
1. **"所有子域等比变慢"= 线程被换了运行环境**，不是代码路径变慢；
2. 查掉速真因的顺序是：**先线程级归属**（谁吃满单核）-> **再核掩码**（Cpus_allowed_list）
   -> **再频率/温度**（cpufreq / thermalservice）。本轮先查频率和温度，全部正常，才被迫往线程方向挖；
3. 掩码是**逐线程**的，不能用 cgroup 或整机视角看——同进程其它线程的掩码会掩盖问题。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 2.3~2.4 节。

### L-069 撤回 L-067 的"主线程跨核迁移"归因（2026-11-23）

L-067 写的是"游戏主线程 `ffrs.gamewindow` 在 cpu3~6 之间来回迁移"。**该具体归因在此撤回。**
线程级采样证明：主线程只占约 5% CPU（10 秒 +43~50 jiffies），
真正吃满单核的是 `dm-gfx`（+811~918 jiffies/10 秒，约 90~100%）。
主线程的迁移与帧率掉速没有因果关系；掉速来自 `dm-gfx` 的核掩码被收窄（见 L-068）。

**教训**：把"某个线程在迁移"当成因果前，先确认**那个线程是不是热点**；
否则会把一个无关线程的正常调度行为当成根因，浪费整轮。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 2.1 节与第 6 节。

### L-070 客机导入是严格白名单 ⇒ 客机改不了本进程的核掩码（2026-11-23）

排查"谁把掩码改成 0x7F"时，客机 NSO 是首要嫌疑，实测排除：

- `src/runtime/hle/nso/nso_call.c:resolve_import` 只放行一个**固定白名单**

### L-071 live-set 字符串开关必须真的把值写进去（2026-11-23）

新增 live-set 开关 `gfxaffinity=prime|big|off` 时，采样脚本里写成
`printf 'gfxaffinity=%s' > gfx-live-set` 而**没有把参数传进去**，

1. live-set 是**字符串开关**时，脚本端必须把值真的拼进去，并在**开跑前**先 `cat` 一次设备上的文件确认；
2. 引擎侧应该把"收到无法识别的取值"也打出来（本轮已经这样打印了空值，才没被静默吞掉）——

### L-073 基线臂必须显式指定核，"系统放置"臂不可复现（2026-11-23）

想拿"不绑核"当基线，实测不可行：系统会在进入重场景后自行把掩码改成 0x7F，
所以"不干预"臂在热态下**等价于绑到 A720 簇**，而且是**不可复现**的（什么时候收窄受设备状态影响）。
可复现的做法是：基线臂显式绑到 big cluster（掩码 0x78），处理臂显式绑到 prime（0x80），
两臂在同一进程内交错。这样基线与处理只差"哪个核"这一个变量。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 4 节。

### L-074 绑核要加异构闸门：同构设备不绑（2026-11-23）

绑超大核在异构 SoC 上是纯收益，但同构 SoC（所有核同频，例如最终目标 RG477M 这类）上
绑一个核没有任何收益，却会让该核不能再服务系统其它工作。
做法：读 `cpuinfo_max_freq` 分档，**只有存在两个不同频率档（prime > second）才绑**，

### L-076 场景覆盖复测要分三档采样，不能只测静止 (2026-11-23)

"这个场景够不够 40 Hz"不能只测静止帧。同一个场景至少要分三档：
**静止 / 特效峰值 / 移动**，三者差距可以很大。
实测月夜火场：静止 50.2~56.6 fps，**攻击特效生效的那几秒掉到 41.0~43.4 fps**

只测静止会得出"这场景很宽裕"的错误结论，真实的最紧一档是特效峰值。
做法：静止 20 轮 × 6 s 连续采样 → 连续触发特效并每秒采样 → 移动中采样，三档都记。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 12.1 节。

### L-077 同一台设备上不要并行跑两个采样脚本 (2026-11-23)

### L-079 一次性的 fps 下跌不能写成场景特性，必须复现 (2026-11-23)

本轮教训：火场曾观测到一段 26 s 的 41.0~43.4 fps 窗口（submit 与 gpu 同时等比放大 ~25%），
第一版结论直接把它写成"战斗特效峰值"。后续两次复现都失败：

不是该场景专属开销；只有某一侧单独放大才指向该路径。

### L-080 引擎自带 gfx-cpu-profile 入口：免改代码取描述符分阶段耗时 (2026-11-23)

排查描述符路径不必改代码重编译：写文件 `files/gfx-cpu-profile`，内容格式

### L-082 引擎自带的「普查类」仪表可能根本没在跑——先证明触发条件成立再信它的数字 (2026-11-23)

### L-083 免重编译的引擎诊断入口清单（ff-resonance 移植引擎） (2026-11-23)

想在不重编译、不重装的前提下量引擎内部，有这些现成入口（都在 app 的 files 目录）：

- `gfx-cpu-profile`：内容 `<起始 present> <帧数> <detail>`。detail=1 开**描述符 21 分段计时**
  （`NVN DESC_TIMING part=…` + `NVN READBACK_TIMING/SITE`）；detail=0 开 CPU 分域计时并**武装计时帧**。

- `gfx-live-ab`：写一个引擎内部路径名（如 `ktag`），运行时**强制该路径处于关闭态**

用法要点：live-set 是**整文件替换**语义，没写到的开关保持当前值；改完必须回读日志确认引擎真的应用了

### L-085 插桩会让「拷贝量」类计数器失真：插桩窗口的数字不能当常态 (2026-11-23)

第 14.4 节那张「texel 全拷贝 8.57 MB/帧、分配 9.32 MB/帧」的表，是在 `gfx-cpu-profile`
插桩窗口里取的。插桩会把 `normal` 置 false，于是 `texel_copy_cache` 的
`cacheable = !compute && normal && graphics_attachment_only()` 闸门失效、拷贝缓存被绕过
（日志里 `NVN PERF texelcopy normal=0` 全为 0 正是这个原因）。
正常会话下同一条日志的真值是 **texel 0.04~1.75 MB/帧、vertex 3.84~4.03 MB/帧**——
**vertex 才是拷贝量的大头（约 80%），texel 不是**。
同理 `READBACK_SITE` 的 `texel-pending fullcopy` 在插桩窗口是 24001 calls / 500 MB，
正常会话下真拷贝只有 3 次/帧、400 KB/帧（其余是帧内复用命中）。

**规则**：凡是用插桩窗口取的**量纲类**计数器（字节数、拷贝次数、分配量），

判据：日志里 `NVN PERF texelcopy normal=0` 是否全为 0——全 0 就说明拷贝缓存被绕过了。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 15.1 节。

### L-086 跨帧缓存的内容变化率有现成计数器：hits vs refresh (2026-11-23)

然后 `NVN PERF pass_ends` 里就有两个互斥计数：

另有 `texel_binds`（走 resident 的绑定数）、`distinct`/`reused`（每帧不同区间数 / 上一帧也用过的）、
`fallback`（退回逐帧快照）、`evict`（被淘汰）四个计数可交叉校验。

**规则**：判断「缓存/增量刷新方向是否成立」时，先找引擎里**已有的互斥计数**（hits vs refresh、

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 15.2 节。

### L-087 中间计数器的下降不等于净收益：必须把整帧所有域加起来 (2026-11-23)

今天差点被一个漂亮的中间数字骗过去：`texmemo=1` 让描述符 `build` 从 10.28 ms/帧降到
5.58 ms/帧（−46%），set 构建 516 → 264 次/帧。若只看这一个计数器，会得出「省了 4.7 ms/帧」的错误结论。
把 `NVN PERF parts_ms_per_frame` 的**所有域**加起来（fire scene 同口径、中位数）才知道真实净差：
descriptor −1.97 ms、hash +0.21 ms、snapshot −0.35 ms、其余 −0.65 ms ⇒ **各域总和 −1.95 ms/帧**。
也就是说：`build` 省下的 4.7 ms 被命中路径的复核成本（hit_total +2.24 ms）与 hash（+0.21 ms）吃回大半。
而且 V1 报告（2026-11-22）早就实测过 `texmemo=0` 在 Honor 上快 1.86 ms/帧——本轮独立复现为 1.95 ms/帧。

**规则**：给任何机制定价，必须用**整帧所有域的净差**，而不是某一个计数器（build / hit / miss）的差。
hit 路径自己也有成本（复核、hash、刷新），这些成本会出现在别的域里。
判法：`parts_ms_per_frame` 把各域加起来 vs `submit_cpu_ms`，两者的差额就是没被归类的开销；
另外用**中位数**而不是均值（热负载窗口会拉偏均值）。
还有一层：净账为正**也不等于该装**——要看这份收益是不是**重复收益**
（引擎当前配置是否已经用更便宜的方式拿到了同样的东西）。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 15.3 与 15.6 节。

### L-089 计时归因不受"每个作用域读两次时钟"影响：detail=0/1 差分可自证 (2026-11-23)

今天差点第二次栽在"插桩假象"上，只是这次栽的是**另一类**。
第 15.1 节已经栽过一次：`gfx-cpu-profile` 插桩让 `normal=false`，**改变了被观测的行为**，
于是 8.57 MB/帧 全拷贝是假的。这次我怀疑的是**归因方式**本身：
每个 `DESC_SCOPE` 都要读两次时钟（`owner->position(root)`），调用次数多的分段
（`element_rest` 12593 次/帧 vs `set_finalize` 524 次/帧）会不会被抬高？

**同一构建、`gfx-cpu-profile detail=1` vs `detail=0` 交错 3 轮**，比 `parts_ms_per_frame` 的 descriptor 值：
r1 **9.47 / 9.47**、r2 **9.53 / 9.53**、r3 **9.63 / 9.44** ⇒ 完全一致，偏差不可测。

**机理**：① `steady_clock::now()` 的取时成本落在时间戳**之外**
（读时间戳之前的调用开销不计入被测区间）；② 子域时间以"根域 children"方式扣除，
根域独占时间对子域开销本身不敏感。

**规则**：怀疑"分段表被插桩抬高"时，**不要凭直觉打折**，用 `detail=0/1` 差分自证——
它只改归因方式、不改行为，两臂的 `parts_ms_per_frame` 应当完全相等。
**要区分两类插桩污染**：改变**被观测行为**的（§15.1，会让数据本身变假），
和只影响**归因方式**的（本条，不影响归因结果）。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 16.6 节。

### L-090 A/B 开关可能是"反向对照"：动手前必须逐个读源码确认语义 (2026-11-23)

今天为"给 692 次/帧的 `snapshot_invalidate` 定价"设计了一个实验：
用 `gfx-live-ab` 写 `snapinval` 把失效关掉，对比有/无失效的开销。
**读源码才发现语义正好相反**：

`@cpp
void snapshot_invalidate(uint64_t address,uint64_t bytes){
    ++snap_invalidations;
    if(ab_off("snapinval")) ++snapshot_epoch;   // <-- 整表清空前端
    ... 只擦重叠条目 ...
}
`@

源码注释也写明：*"bumping the epoch there (A/B target snapinval) emptied the whole front
on every in-stream CPU write, overlapping or not."*
⇒ `snapinval` 是「把失效做成**最坏情况**」的对照开关，**不是**「关掉失效」。
**正常路径才是「只擦重叠条目」**（实测 erased 仅 1.5~2.0/帧，而失效调用 697~700 次/帧）。

**规则**：`ab_off(name)` 的名字只表示"让这条路径走 `ab_off` 分支"，
**不表示"这个开关关掉某功能"**。设计 A/B 之前必须先读该分支的代码与注释，
否则会拿一个"把事情做坏"的开关去当对照组，结论全反。
**判法**：先在源码里找到 `ab_off("name")` 的所有出现处，读它所在的那一行到底做了什么。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 16.3 节。

### L-091 "省拷贝"的机制未必划算：省下的 memcpy 可能比算哈希还便宜 (2026-11-23)

今天测 vcache：关掉它，vertex 拷贝从 3.90/4.06 MB/帧 涨到 6.35 MB/帧，
即它**确实**省下 2.29~2.45 MB/帧 的 memcpy。但四个臂位的
`submit_cpu_ms`（18.99~19.81）与 `fps`（44.01~46.51）**全在噪声内**。

**机理**：`vcache` 每次命中都要对**全部内容**逐字节算 FNV-1a（`fast_buffer_hash`）。
它省的 2.4 MB memcpy 按 40+ GB/s 算只有 **约 50 µs/帧**，
而哈希 2.4~3.0 MB 的成本与它同量级 ⇒ 两者相抵。
⇒ 由"能省字节"推不出"能省时间"：**字节量要换算成带宽时间再比**。

**规则**：给"省拷贝"类机制定价时，先估算
**memcpy 的时间 = 字节数 / 实际带宽**，再和**验证/哈希那一步的成本**比。
两者同量级时，这条机制就是净中性，不值得为它改代码。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 16.2 节。

### L-092 desc_memo_reset() 每帧被调用约 708 次，并连带整表清空 img_cache (2026-11-23)

今天在追"img_cache 为什么每帧 miss 244 次"时发现的结构：
`desc_memo_reset()` 的第一行就是 `img_cache.clear()`
（除非 `honor_img_cache_persist_experiment` 为真），
而它每帧被调用约 **708 次**：

| 调用方 | 每帧次数 |
|---|---|
| `snapshot_invalidate()` | 697~700 |
| `snapshot_reset()`（每 submit 一次） | 9.75 |

⇒ **img_cache 每帧被整表清空约 708 次**，这就是 miss 高达 244/帧的原因。

**另有一处安全性问题**：`img_cache` 条目持有指向纹理池的
`const RegisteredTexture*`，跨池复用会悬垂；`size()>4096` 只是兜底闸门，不是真解。

**规则**：看到"某个缓存命中率异常低"时，先查**它被谁清空、清空多少次**，
再决定是优化缓存还是优化清空；清空次数是帧级计数器（`desc_memo_reset` 的调用方），
比缓存命中率更早暴露问题。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 16.4 节。

### L-093 热负载下的噪声底：CPU 侧 <1 ms/帧 的改动判不了 (2026-11-23)

### L-094 GPU 侧计时比 CPU 侧稳定得多：热负载下 GPU 结论照样能出 (2026-11-23)

今天用 `gfx-pass-live`（免重编译的逐帧 GPU pass 计时）采样 5 帧，

### L-095 用「给 CPU 加负担」区分「GPU 空转等 CPU」与「GPU 真在干活」 (2026-11-23)

测到一段 GPU 时间「落在所有 render pass 与 compute dispatch 之外」时，
最自然的解释是 **GPU 追上了 CPU 然后空转等待**（因为本项目 CPU 是瓶颈）。
判法：**给 CPU 加一段已知的工作量，看这段空档会不会跟着涨**。

今天用 `descmemo=0`（第 14.3 节实测 +0.9 ms submit_cpu）做交错 A/B：
submit_cpu 17.78 → 19.06 ms（+1.28）、fps 49.4 → 45.7（−3.6），
而空档 **2028 / 2022 / 2032 / 2031 µs —— 纹丝不动**。
⇒ 排除「空转等待」，它是真实发生在 GPU 上的工作。

**规则**：看到「一段无法归类的时间」时，先问它是**等待**还是**工作**；
用一个只改变 CPU 负载、不改变 GPU 工作的开关做一次 A/B 就能分开。
判据：空档随 CPU 负担变化 ⇒ 等待；不变 ⇒ 工作。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 17.5 节。

### L-096 GPU 往主机可见内存写，比 CPU memcpy 还慢 2.4 倍 (2026-11-23)

今天定位到的一条 GPU 侧大头：存储写回路径每帧分配 **9.32 MB** 的读回缓冲
（`READBACK_TIMING alloc_bytes`，430 次/帧），而读回缓冲分配在
**HOST_VISIBLE | HOST_COHERENT | HOST_CACHED** 内存上 ——
所以 **GPU 是直接往主机可见内存里写结果**。

带宽核对：

| | 字节 | 耗时 | 带宽 |
|---|---|---|---|
| GPU 写主机可见内存 | 9.32 MB | 2.0 ms | **4.66 GB/s** |
| CPU memcpy 同样字节 | 7.1 MB | 0.64 ms（冷） | **11 GB/s** |

⇒ **GPU 写 host-visible 比 CPU memcpy 还慢 2.4 倍**（移动 GPU 写主机可见内存
不可缓存、不可压缩、不走 tile）。算出来的 2.0 ms 与实测空档（2011~2032 µs）吻合。

**规则**：估算"某条搬运路径"的代价时，**先看它落在哪种内存上**——
device-local、host-visible、host-cached 三者的 GPU 带宽可以差数倍。
把字节数除以对应带宽，就能直接预测它值多少毫秒；
再用引擎自己的计数器（`alloc_bytes` / `copy_bytes` / 写回 MB）核对总量。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 17.6 节。

### L-097 读回流量必须按站点拆开统计，总量会把 93% 落错地方 (2026-11-23)

第 9 轮用 `NVN READBACK_TIMING` 的**总量**（alloc_bytes 9.32 MB/帧），
把 GPU 空档归因到「存储写回路径」，并据此定了方案 A（写回目的地改 device-local）。
第 10 轮改读引擎自带的**分站**表 `NVN READBACK_SITE v=1 site=...`，结论相反：

| 站点 | alloc MB/帧 | 占比 |
|---|---|---|
| texel-pending | 8.34 | **93%** |
| texel-CPU | 0.63 | 7% |
| storage-CPU-preserve | 0.14 | 1.5% |
| storage-pending-fullcopy | 0.041 | 0.4% |

总量一模一样，**落点差 5 倍**——真正的"存储写回"只有 0.18 MB/帧。

**规则**：引擎有分站计数器时，**禁止用总量做归因**。
先按站点拆开，再谈"哪条路径贵"；总量相同而归因不同的情况本项目已经犯过一次
（第 9 轮），必须按 AGENTS.md 显式撤回。
**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 18.1 节。

### L-098 屏障有去重：「调用次数」不等于「实际发出次数」 (2026-11-23)

`full_barrier()` 开头有去重：`barrier_seq==write_seq && last_finish_ops==perf.ops` 就直接 return。
所以 texel-pending 每帧 156 次拷贝调用，实际只发出 **52 次** full barrier，
另外 **104 次被跳过**（`NVN PERF texel_pending bar_full=52.0 bar_skip=104.0`）。

**规则**：估算屏障/同步代价时，用**引擎自己的发出计数**，不要用调用点计数。
把「每次调用都发一次屏障」当默认假设，会把屏障成本高估 3 倍。
**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 18.4 节。

### L-099 GPU 时间戳会把「GPU 等 CPU」计进 pass 耗时，不能直接拿来 A/B (2026-11-23)

用 `gfx-pass-live` 采样时，同一个 pass（slot5 i=5，draws/verts 逐帧完全相同）
耗时在连续帧里从 **2408 µs 涨到 5485 µs**；而且**每次采样窗口的形状一模一样**
（前 8 帧低、第 9~12 帧爬升、之后稳定）。⇒ 这是与「开启采样」绑定的**测量伪影**，
不是场景变化。而且稳定后的「27 ms/帧」已经超过当时的帧周期（18.5 ms），
物理上不可能是纯 GPU 执行时间。

**规则**：**先证明时间戳量的是"纯执行"而不是"含等待"**，
判法：同一个 pass 的耗时是否在帧间单调爬升且与负载无关。
这类计数只能用来做**同一次采样内的相对比较**，
跨采样做 A/B 前必须先确认两边都落在稳定段（跳过前 8 帧）。
**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 18.6 节。

### L-100 先看线程占满度找瓶颈，别先看 GPU (2026-11-23)

本轮最快的定位来自 `/proc/<pid>/task/*/stat` 两次采样差分（每线程 utime+stime）：

| 线程 | 占单核 |
|---|---|
| **dm-gfx** | **93.8%** |
| RHIThread | 35.2% |
| RenderThread 0 | 33.4% |
| GameThread（多个合计） | ~102% |

而同一时刻 GPU 只有 10~12 ms/帧（帧周期 18.5 ms）⇒ **瓶颈在图形线程的 CPU 侧**。
`NVN CPU_TIMING part=...` 的独占时间合计 **18.30 ms/帧**，与 dm-gfx 的占满度完全吻合，
并直接给出逐域账：descriptor 8.67 / other 2.92 / snapshot 2.44 / draw 1.41 / cleanup 1.18 …

**规则**：拿到"帧率上不去"时，**第一步量每线程占满度**（两次 /proc 差分，10 行脚本），
第二步用引擎的**逐域 CPU 计时**对账。
比"先猜 GPU 侧、GPU 侧没有就猜 CPU 侧"快一个数量级。
**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 18.7~§18.8 节。

### L-101 面板刷新率是硬上限：先确认测量场景有没有被 vsync 顶住 (2026-11-23)

`dumpsys display` 显示 Honor 当前模式是 **60.000004 Hz**
（SurfaceFlinger `FPS min:60 max:60 cur:60`；设备其实支持 90/120/144 Hz）。
第 1 章场景 fps 54~60 ⇒ **已经贴着上限**，
渲染侧省下来的时间**换不来帧率**，却会让 A/B 变成"什么都测不出来"。

**规则**：任何"优化渲染换帧率"的 A/B，开跑前先确认三件事：
① 面板当前刷新率；② 该场景 fps 离上限还有多少；③ 若已贴顶，
改去**没贴顶的场景**（本项目是兵工厂深处 43.8~48.7 Hz）测，或明确写成
"本轮只测余量不测帧率"。
**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 18.7 节。

### L-102 A/B 必须用交替窗口的配对差：热漂移 0.17 ms/臂 (2026-11-23)

本轮把 6 个臂按时间顺序排开测，`gpu_ms` 单调上升 9.85 → 10.80（**0.17 ms/臂**），
看起来像"每个臂都在变差"；改成 **A/B 交替 6 s 窗口 + 配对差**后，
窄屏障的真实差值是 **submit +0.01 / gpu +0.01 / fps +0.03 ms** —— 完全中性。

**规则**：多臂测量**不要顺序排开**（热漂移会把臂差和漂移混在一起）。
用交替窗口 A/B/A/B…，报**配对差**；顺序排开的均值只能当参考。
同时：**边际成本探针**（把一条拷贝/屏障重复一次，看差值）比"总量 ÷ 带宽"可靠得多，
因为后者依赖一个从没被单独测过的带宽假设（本案里 4.66 GB/s 就是错的）。
**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 18.5~§18.6 节。

### L-103 用 intent extra 确定性地回到某个未触顶场景，比手动导航可靠 (2026-11-23)

引擎自带隔离存档恢复入口（`src/android/app/java/org/ffrs/diagnostic/RegressionSaveRoot.java:11~28`）：
`am start ... --ez isolated_regression_save true --es isolated_regression_resume shield-regression-<数字>`
即可从 app 私有目录里的那个存档继续。设备上现成可用：
`shield-regression-20261118094001` = **第 4 章兵器工厂熔岩场景**（fps 45.8~48.6，未触 60 Hz 顶）。

**规则**：性能测量前先确认"这个场景有没有被面板刷新率顶住"（见 L-101）；
如果被顶住，**不要在它上面做 A/B**——换场景。
换场景优先用**存档恢复**而不是手动导航：手动走位不可复现，而存档恢复是确定性的
（本项目此前只在 QA 轮次用过这个入口，性能轮次一直缺一个可靠的"未触顶场景"）。
**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 18.11 节。

### L-104 别用「总量 ÷ 假设带宽」给 GPU 搬运定价，用"重复一次"的边际成本探针 (2026-11-23)

在兵工厂这个未触顶场景里，用"把同一条 `vkCmdCopyBuffer` 重复一次"测出：
**每帧多搬 9.5 MB 的 host-visible GPU→GPU 拷贝，代价 <0.03 ms**（gpu_ms 差 −0.001 ms）。
若按第 9 轮反推出来的 4.66 GB/s 算，这 9.5 MB 要 2.0 ms —— **高估了 60 倍以上**。
移动 GPU 上 host-visible 与 host-cached 内存走统一内存，GPU→GPU 拷贝接近 LPDDR 带宽，
远比"写主机可见内存"这类估算暗示的便宜。

**规则**：给 GPU 搬运路径定价，**只能靠重复一次的真实边际成本**；
"总量 ÷ 带宽"里的带宽必须是**在本设备实测过的**，否则会系统性高估并把优化引到错误的靶子上
（第 9 轮就是这样把 9 轮的工作指向了一条 41 KB/帧 的"方案 A"）。
**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 18.11 节。
### L-105 缓存命中率不是「慢路径」的证据：先分清 miss 代价与每次调用的固定成本 (2026-11-23)

兵工厂场景 descriptor 域 image_lookup 占 2.18 ms/帧（3951 次/帧），
看起来像「图像查找很慢」。分站后：img_cache 命中 1842.8 / 未命中 230.1（89% 命中），
texture_record 前端命中 3893.2 / 未命中 120.3（97% 命中）——
**未命中只占 5.8%**，且 `get_image()`（xbg_game.cpp:3155）与 `pool_key()`（2833）
已有直映前端缓存。⇒ 这 2.18 ms 是**每次调用都要付的固定成本**
（8 字段 ImgKey 构造 + 哈希 + 比对），不是 miss 路径的代价。
第 8 轮「让 img_cache 持久化」把 miss 归零只换来 +0.2 ms（低于噪声），与此一致。

**规则**：看到某个缓存命中率高，**不能**直接推出「慢路径便宜」或「慢路径贵」。
必须先分清三件事：① 调用总次数；② miss 次数；③ **每次调用的固定成本**。
固定成本主导时，优化 miss 是白干（调用次数不降）；此时该看的是
「能不能减少调用次数」或「能不能让固定成本变便宜」（更小的 key、免哈希、免构造）。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 19.2 节。

### L-106 未归因余量先拆到子域再动手 (2026-11-23)

`other` 域 3.94 ms/帧、`snapshot` 域 3.11 ms/帧 —— 这两块只有总量和调用次数，
没有更细的粒度。`other` 尤其可疑：它是帧函数（xbg_game.cpp:9344）与 present 回调
（:9669）上的**根 scope**，标签 `CPU_SCOPE(Other)` 覆盖了这两段里**所有没有被
子 scope 归因的余量**（`xbg_cpu_timing.h` 的 Scope 用 exclusive = elapsed − children
计算）。所以「other 大」只说明**有 3.94 ms 落在没人认领的地方**，不说明它是什么。

**规则**：拿到一个**未归因余量**（other / remaining 这类聚合域），
**先加计时子域把它拆开，再决定改什么**；不要因为它数字大就整块重写或做激进旁路。
拆分的成本是一轮构建周期；拆不开就等于没有目标。
（与 L-092「小收益不占构建周期」配合：先拆、再判断值不值得优化。）

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 19.4 节。

**已验证（2026-11-23 第 11 轮）**：这条规则直接命中——`other` 域拆开后
**4.21 ms/帧（23.5%）是 execute() 的 NVN 命令解释开销**，`snapshot` 域拆开后
**2.57 ms/帧是慢路径**（38.4% 的调用没命中直映前端）。两者都是前 10 轮完全看不见的。
### L-107 插桩本身会虚增被测域：先看引擎自报的 clock_reads (2026-11-23)

第 10 轮用 `gfx-cpu-profile` 的 **detail=1** 模式读到 descriptor 域 **7.52 ms/帧**，
本轮同一场景改用 **detail=0** 读到 **4.61 ms/帧**，差 3.0 ms/帧。
根因不是业务代码变了，是**测量工具本身**：
`detail=1` 打开 `XbgDescriptorTiming` 的 24 个子域，每个子域构造与析构各调用一次
`root->recorder->clock()`；引擎自报 `NVN DESC_TIMING v=2 ... clock_reads=3412856`
= **56,881 次时钟读/帧**，全部落在 descriptor scope 内部。

**规则**：**比较不同测量模式的数字前，先看引擎自报的 `clock_reads`**，
用「clock_reads/帧 × 时钟读成本」估算插桩开销并从读数里扣掉。
**绝对值一律用 detail=0 取**（或扣掉插桩开销），**detail=1 只用于子域归因**。
同理：任何「某域变贵了」的结论，都要先确认两次测量的插桩档位相同。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 19.9 节。

### L-108 聚合域的均值会掩盖尖峰：先看单次峰值，再看均值 (2026-11-23)

`other` 域第 10 轮读数为 3.94 ms/帧、9.4 次/帧、均值 419 µs、单次峰值 11.15 ms。
均值看起来平平无奇，**峰值是均值的 27 倍**。
第 11 轮拆开后才知道：这是 `execute()` 的 NVN 命令解释开销，
其中**偶发一次 10 ms 的巨型提交**（8.6 次提交里的 1 次），其余每次只有几百 µs。
⇒ 真正的问题是**偶发尖峰**，不是每帧的均匀开销。

**规则**：看一个聚合域的账时，**峰值与均值要分开读**：
峰值远高于均值 ⇒ 攻「找并消除尖峰」（哪一次调用、哪一类输入）；
峰值与均值接近 ⇒ 攻「降低每次调用的固定成本」。
两者的优化手段完全不同，混在一起就会像本项目前 10 轮那样盯着均值找错了靶子。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 19.8 节。
### L-109 聚合域的「独占时间」会把命令体与解释器混在一起，必须再按 op 拆一次 (2026-11-23)

第 11 轮把 `other` 域拆出 `sub_exec` = 4.21 ms/帧，据此写成「other 就是 execute() 的
**命令解释开销**」。第 12 轮把 `execute()` 再拆到 op 级后，这个措辞被**修正**：
解释器自身其实很便宜（头解码 51 ns/命令、arena 检查 50 ns/命令），
贵的是**命令体里做的事**（`OP_DRAW_IDX` 16.15 µs/次 × 679 次/帧 = 10.96 ms/帧，
`OP_DISPATCH` 2.85 ms/帧）——它们此前被 `sub_exec` 的「独占时间」口径一起算进了「解释器」名下。

**规则**：`CPU_SCOPE` 的**独占时间 = 区间时长 − 子 scope 区间**，所以它会把
「本层自己的逻辑」与「本层调用到的、但对方没有 scope 的工作」混在一起。
**要判断是谁在花时间，独占时间不够，必须把被调用的动作按类型再计一次**
（本项目用「按 op 累计耗时 + 单命令最大值」实现）。
特别是：一个域里如果大部分时间其实是**调用别人**的时间，
那这一域的名字（exec / decode / dispatch）会误导方向。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 20.4~§20.5 节。

### L-110 尖峰的成因要看「条数与耗时的比例」，不能只看条数 (2026-11-23)

第 12 轮先以为 10 ms 的尖峰是「某次提交带了 6,844 条命令」造成的；实测：
命令条数最多的那次提交（6,844 条）只花 10.42 ms，
**最慢的那次提交（18.52 ms）却只有 2,450 条命令** ⇒ 条数与耗时不构成比例，假设被否。
真正的尖峰在 `poll_retire` → `retire_slot` → cleanup（cleanup 单次峰值 **9.37 ms**）。

**规则**：看到「某次调用特别慢」时，**必须同时记录两个量**：这次调用的**规模**
（条数、字节数、调用次数）与**耗时**，并看两者是否成比例。
成正比 ⇒ 优化单位成本；不成比例 ⇒ 尖峰来自**另一个维度**（等待、锁、驱动调用、清理），
去优化单位成本是白干。本项目这次差点又走错路。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 20.4② 节。
### L-111 计时插桩自身有成本：每个窗口都要与引擎的独立计时对账 (2026-11-23)

**现象**：第 13 轮加到 34 个 CPU 子域，窗口内 **61,168 次 scope 进入/帧**。scope 树实测 `measured` = 22.603 ms/帧，
而引擎自己那条**不依赖 scope 机制**的计时（`NVN PERF v=1` 的 `submit_cpu_ms`）报 **21.18 ms/帧**，差 **1.42 ms/帧**。

**错在哪**：把 scope 树里的数字直接当「真值」读，插桩成本就被算进了被测域。
第 10 轮已经栽过一次（detail=1 的 descriptor 子域虚增 3.0 ms/帧），本轮差点重蹈。

**正确做法**：每个采样窗口都同时读两行 —— scope 树的 `measured_ns`，以及引擎自己那条独立计时（PERF 的 `submit_cpu_ms`）。
两者之差 = 本轮插桩总开销；再除以本窗口的 scope 进入次数，得到**单次进入成本**（本轮实测 **23 ns**）。
所有「每命令 / 每调用」级别的数字先减掉这一块再解读。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 21.3 节。

### L-121 判断「这个区间会不会和任何条目重叠」用页覆盖集合，比端到端包络有效得多 (2026-11-23)

**现象**：引擎里现成的快路径 `bboxready` 用**一个 `[min,max]` 包络**覆盖全部 pending 条目，
而这些条目的地址跨度有 **2.8 GB** ⇒ 包络几乎等于没有，只能跳过 18.2% 的扫描步。
换成**页粒度（4 KB）**就能精确回答同一个问题：
「`[addr, addr+n)` 覆盖的页里有没有被占着的页？」没有 ⇒ **可证明无重叠** ⇒ 跳过整个线性扫描，
而且**这个结论与跑完线性扫描完全一致**，语义不变。

**规则**：给「一对多的区间查询」做保守早退时，**早退判据要和查询区间同粒度**。
全局包络（min/max）在地址跨度大时几乎无效；**分桶/分页的覆盖集合**才既精确又 O(1)。
维护成本按「条目总字节 ÷ 页大小」估（本项目约 2,400 次页级增减/帧 ≈ 0.06 ms/帧），只要远小于省下的扫描就划算。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 22.6 / 23.5 节。




### L-122 一对多的区间查询：用「带子树最大 end 的平衡树」替线性扫描，维护成本与条目大小无关 (2026-11-23)

**现象**：pending 列表（帧内写回约 391 条 + 报告约 94 条）被问「这段地址有没有被 pending 覆盖」
约 7,260 次/帧，每次线性扫描整张表。

**规则**：键取（区间起点, id），节点存**自己子树里最大的 end**，查询时凡是「子树最大 end ≤ 查询起点」
的整棵子树直接剪掉，一次查询只访问 O(log n + k) 个节点（k = 命中条目数，通常 0）。
**id 在 push 时分配**，于是「最新一条命中者胜出」这条规则直接用 id 比较即可，不必另外维护顺序。
维护是**增量**的：每个变更点一次 insert / erase，O(log n)，**与条目覆盖多少字节无关**。

**为什么不用页覆盖过滤器**：页方案（4 KB 页 → 引用计数）的维护成本正比于每帧写回的总字节数
（本项目约 9.3 MB/帧），条目一大就变贵；树方案只随**条目条数**增长。
实测：节点访问 89,163/帧（15.5 个/查询）、增删 786 次/帧，索引自身 ≈ 0.22 ms/帧。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 24.1 / 24.3 节。

### L-123 插桩窗口里的「域独占值」会系统性偏高；真实成本必须用同会话交错 A/B 读 (2026-11-23)

**现象**：在带 61,168 次/帧作用域进入的插桩窗口里读出「pending 扫描 = 2.05 ms/帧」；
去掉插桩后用同会话交错 A/B 实测，把扫描换成索引只省下 **0.68 ms/帧**

### L-130 「分段敏感度」：判定一段 CPU 工作在不在关键路径上，必须分段注入 (2026-11-23)

### L-131 敏感度最高的段 ≠ 可优化靶子 (2026-11-23)

**现象**：敏感度最高的 cleanup 段（1.645）里，1.69 ms/帧 主要是

### L-132 一笔 CPU 优化的边际价值 = 该段敏感度，不是该段大小 (2026-11-23)

**现象**：draw 段占 11.13 ms/帧（最大头），敏感度只有 0.700 ⇒ 每省 1 ms 只换 0.70 ms 帧周期；
dispatch 段只有 3.18 ms/帧，敏感度 1.459 ⇒ 每省 1 ms 换 1.46 ms 帧周期。

**规则**：选靶按「**可省量 × 该段敏感度**」排序，并先问「这段工作落在 GPU 空档里还是之外」；

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 27.5、27.9 节。

### L-133 引擎里并行的同名站点路径，探针要分别挂，否则漏数 (2026-11-23)

**现象**：引擎有**两条并行**的快照慢路径：通用 `snapshot_slow()`（808 次/帧）与

### L-134 敏感度是会话热状态的属性，不是常数 (2026-11-23)

**现象**：同一段、同一场景、同一引擎，三个会话测出的 dP/dBurn 明显不同：

### L-135 注入探针的段位必须与引擎枚举一致，且要核对 mask 与烧录量 (2026-11-23)

**现象**：脚本按「插入位置」把新段编成第 5 位（位值 16），引擎里它其实是第 7 位（位值 64），

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 28.5 节。

### L-137 撤回一条收益估计时，要同时撤回它的下游推论 (2026-11-23)

### L-138 嵌套 scope 的站点表不能直接相加，小站点要先扣掉插桩开销 (2026-11-23)

**现象**：§27.7 把 `snapshot 0.82` 与它的子站点 `sub_snap_fast/slow/map/stream 0.61/1.64/0.20/0.83`

### L-139 帧周期 ≠ submit_cpu：差额是「等来宾」的空档；用逐线程 CPU 把两边分开 (2026-11-23)

**现象**：兵工厂帧周期 23.8 ms、引擎自报 submit_cpu 20.1 ms，差的 ~4.3 ms 一直没人归因。
这台设备上 `perf_event` 完全不可用（`simpleperf` 的 `cpu-cycles` 与 `cpu-clock` 都被拒），
栈级采样做不了。改用 `/proc/<pid>/task/<tid>/stat` 的逐线程 tick 差值：
tick→毫秒**用引擎自己的 `submit_cpu_ms` 交叉标定**（本机 CONFIG_HZ≈250，不是 100）。
⇒ 引擎 dm-gfx 线程 **19.5 ms/帧（占帧周期 82%）**，来宾 RHI 线程 6.5 ms/帧、其余来宾线程合计 ~15.4 ms/帧
（与引擎并行，不叠加）；`block_ms legacy_wait` 那 3.95~5.68 ms/帧是**来宾等自己的 fence**，不是引擎在等。

**规则**：判断「该优化引擎还是该优化来宾」时，先把帧周期拆成「引擎 CPU + 等来宾的空档」；
`perf_event` 不可用时用逐线程 tick 差值（**必须用引擎自己的时钟标定 tick 频率**）；
同时注意 `block_ms` 里各 site 的归属方（引擎的等待 vs 来宾的等待）。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 29.3 节。

### L-140 抽样计时的报数是「抽样和」，总量要乘抽样率 (2026-11-23)

**现象**：V19 给 NVN API 层定价时，报数行是 `NVN PERF nvnapi rec_ms=0.029 rec_calls=10856 rec_mean_ns=170.8`。
照字面读是「API 层每帧只花 0.029 ms」；但 `rec_ms` 是**被抽样的那些调用**的耗时之和，
抽样率是 1/64 ⇒ 真实总量 = **64 × 0.029 = 1.86 ms/帧**（每次录制 ~170 ns，被抽样的调用还要多付两次时钟读，
扣掉后 ~115 ns ⇒ 真实 ~1.3 ms/帧）。**照字面读会把一个 1.86 ms/帧的池看成 0.03 ms/帧，差 60 倍。**

**规则**：抽样计时的报数必须**紧挨着写抽样率**，并同时给出「抽样和」与「外推总量」两个数；
字段名要能区分（如 `rec_sampled_ms` vs `rec_total_ms`）；外推前先扣掉抽样调用自身的探针开销

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 30.2 节。

### L-141 先看关键线程的 R/S 态，再决定优化谁 (2026-11-23)

**现象**：引擎的 dm-gfx 线程每帧用 19.5 ms、帧周期 23.8 ms（82%）。这既可能是
「它自己饱和了」，也可能是「它忙 82%、另外 18% 在等来宾」—— 逐线程 CPU **分不出这两种**。
而这两种情况指向完全不同的优化方向。
本轮采了 120 次 `/proc/<tid>/stat` 的 state 字段（6 s）：**114 R / 6 S** ⇒ 线程 95% 的时间在运行，
没有阻塞 ⇒ 它是限制者，来宾的产命令速度不是瓶颈 ⇒ 跑在来宾线程上的 NVN API 层
（实测 1.3~1.9 ms/帧）**不在帧周期关键路径上**，方向直接关闭，省掉一个构建周期。

**规则**：优化一个「跑在别的线程上」的成本之前，先确认关键线程是否真的阻塞在它上面；
判据是 `/proc/<pid>/task/<tid>/stat` 的 state 字段（R/S）采样（120 次 / 6 s 足够），
配合逐线程 tick 差值（tick→ms 要用应用自己的时钟交叉标定，本机 CONFIG_HZ≈250，不是 100）。
另外：`perf_event` 可能整个不可用（本机 simpleperf 的 `cpu-cycles` 与 `cpu-clock` 都被设备拒绝），
这时 `/proc` 是唯一可用的归因手段。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 30.3 节。

### L-142 站点表的 exclusive 与 inclusive 必须一起读：父站点自有 ≠ 探针开销 (2026-11-23)

**现象**：第 21 轮把三个 per-command 探针站点（`sub_cmd_decode`/`sub_poll_retire`/`sub_arena_check`，
各 10864~11054 次/帧、每次 51~61 ns）判成「基本等于插桩自身的 scope 开销」，
于是把整个命令解释器判成「真实逐命令开销只有 ~0.5 ms/帧，不是可动的靶子」并写进了退役清单。
第 23 轮在同一场景取到 `NVN CPU_TIMING` 的 **inclusive_ns** 后才发现算错了：
`sub_exec` 的 **exclusive = 4.423 ms/帧**（inclusive 24.10），每帧 10873 条命令 ⇒ **解释器自有 ≈ 407 ns/命令**；
那三个站点合计 1.78 ms/帧 基本是探针开销，**但父站点的 exclusive 是真实工作，不能一起扣掉**。

**规则**：
- 站点表（`NVN CPU_TIMING` / `NVN DESC_TIMING`）**必须同时读 exclusive 与 inclusive**：
  只有「子站点的探针开销」可以扣，**父站点自己的 exclusive 是被测对象的工作量**；
- 扣探针开销时，按「每站点 × 每次探针成本」逐项算，并**写下扣前扣后两个数**；
- 「某个域只剩插桩量级」这种结论，会把**最大的一池**误判成没有价值——本例直接误杀了引擎里第二大的池。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 31.2 节（撤回 C）与 31.5 节。

### L-143 诊断计数器的名字要看语义：「跨帧复用数」≠「缓存命中数」 (2026-11-23)

**现象**：`NVN PERF pass_ends` 里的 `texel_binds=1330 distinct=309 reused=67` 被第 22 轮读成
「per-slot 视图缓存每帧只命中 67 次」⇒ 推出「每帧约 1250 个 `VkBufferView` 被创建」⇒ 推出
「视图创建值 2~4 ms/帧，值得做跨槽共享」。实测**两条都错**：
`reused` 的定义是「本帧用到的不同区间里，上一帧也用到的个数」（`texel_frame_keys` 与 `texel_prev_keys` 的交集），
**与视图缓存的命中无关**；视图创建的真实次数是 **869.2 次/帧**、创建耗时 **0.356 ms/帧**，
视图缓存查找 1883.9 次/帧 ⇒ **真实命中率 53.9%**（1014.7 次/帧）。

**规则**：

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 31.2 节（撤回 A）。

### L-144 用「同一操作的两个开关臂」做差分分解：差值就是开关的价值 (2026-11-23)

**现象**：`image_lookup` 是 descriptor 域最大的子站点（2.18 ms/帧、4018 次/帧），但它是个黑盒。
解法不需要新插桩：**同一场景、同一帧结构**下取两个臂——A 臂缓存开、B 臂用**启动期标记**关掉图像缓存——
各取一个 `NVN DESC_TIMING` 窗口，然后做差：

- 差值 = 该缓存今天的价值 = **0.78 ms/帧**（(2.333+0.788) − (2.178+0.160)）；
- 每次命中改成未命中**多付 423 ns**（视图 + 布局过渡 + 采样器三项）；
- B 臂还顺带暴露了「作用域覆盖 4018 次/帧里其实有 1945 次走的是另一个分支」。

**规则**：
- 分解一个黑盒域，优先找**已有的运行时开关**做两臂差分，而不是先写新探针（省一个构建周期）；
- 差分必须**同一场景、同一帧结构**，并用计数器证明开关真的生效（如 B 臂 `img_cache_hits=0`）；
- 开关若是**启动期**语义（如 `gfx-no-imgcache`），窗口只能在启动后取，且要用**两次启动**取两个臂
  （`live_profile_used` 这类窗口**每进程只能 arm 一次**）。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 31.4 节。

### L-145 作用域覆盖的调用数 ≠ 走某条分支的调用数 (2026-11-23)

**现象**：`image_lookup` 的作用域覆盖 4018 次/帧，初稿据此写成「1945 次/帧是不可缓存的图像绑定，

- 站点之间口径不同就分列（本轮 `texel_cpu_access` 12 次/帧 与 snapshot 路径 `cpu_access` 2379 次/帧 是两回事）。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 35.2、35.3 节。
### L-162 诊断 Activity 必须显式给游戏目录，否则 guest **静默不启动**（2026-11-23）

**现象**：Honor 与 RG477M 启动后画面停在「数据安装与自动发现」页，`engine.log` 时间戳不推进，

### L-163 跨版本像素对照的前提是**机位对齐**，否则只能判「视觉一致」 (2026-11-23)

在 Honor 上用优化前基线 1.0.73 与 V21 对照同一存档同一分辨率时，两版**镜头站位不同**，
25 组交叉匹配的最佳配对仍有 mean|d| 18.54；差异最大处其实是「同一处火光在两版里屏幕位置不同」，
而不是特效丢失。

**规则**：
- 跨版本/跨设备像素对照**必须先量同版本的帧间漂移基线**：本轮 1.0.73 自比 median 2.41、V21 自比 median 20.27，
  说明镜头在动 ⇒ 差异不可归因到特效；
- 机位无法自动对齐时，**改用人工走位固定站位**（agent 负责读档、取帧、测帧率，人工负责操作），
  比反复尝试自动走位更快也更可靠；
- 「视觉一致」（逐项目视确认特效层都在）与「像素一致」是两种强度不同的结论，**不要混着说**。

**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 36.3 节。

### L-165 A/B 读数必须用窗口值：「会话累计均值」会把真实差异洗掉 (2026-11-23)

`NVN AB aff` 打印的 fps = `A.frames / A.wall_ns`，而这两个计数**跨整个会话累积**（只在 affinity 模式切换时复位）
⇒ 它的读数是**会话累计均值**。用它做 A/B 判定时，切换前后的差异会被历史帧稀释掉，
本轮第一次 A/B（honorimgpersist）就是这样得出了「无变化」的**无效结论**。

**规则**：任何开关 A/B 一律用 `NVN PERF v=1` 的 **60 帧窗口值**（`fps=`、`submit_cpu_ms=`、`gpu_ms=` 同在一行），
且必须 **A→B→A→B 配对**判读（看配对符号，不看绝对值差）；窗口读数噪声实测 ±0.5 fps（与设备热漂移同量级），
小于该幅度的差异一律记为「无增益」。
**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 37.3 / 37.4 节。

### L-166 镜像缓存 miss 方向证伪：misses 357→0/帧，帧率不动 (2026-11-23)

`honorimgpersist`（运行时 live 开关）把 img_cache 的 misses 从 ~357/帧压到 **0/帧**，
img_cache_hits 由 4006 升到 4369（机制确实生效），但**帧率不变**。
⇒ `image_lookup` 的 2.149 ms/帧**不在 miss 路径上**，而在命中路径的每调用固定成本上；
再往「miss 方向」加缓存、加池、改键都无效。
**规则**：缓存类优化先用「把 miss 压到 0」的运行时开关验证**上限**；若上限也不动，直接退役该方向，不要再写代码。
**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 37.5.1 节。

### L-167 帧率缺口先分「worker 提交账」还是「GPU 等待账」：submit_cpu_ms 才是 worker 的账 (2026-11-23)

`perf.submit_cpu_ns` 在 `xbg_game.cpp:9665-9678` 累加，范围是**异步翻译线程整段提交**
（从 `begin` 到提交完成，含 `execute()` 的命令循环），**不是 guest 线程耗时**。
本轮据此判定：兵工厂战斗场景 31.5~32.0 fps 里，worker 的 25.8~28.1 ms/帧是**唯一**瓶颈
（GPU 14.9~18.8 ms 被掩盖），缺 40 Hz 是「**还要再砍 6.3~6.8 ms/帧**」，而不是「等 GPU」。
配套判读法：长帧日志里 `gap_ms ≈ submit_cpu_ms + gpu_ms` ⇒ 该帧 CPU 与 GPU **未重叠**（各自都在跑满），
这种帧不是单侧慢，而是**流水线被切断**。
**规则**：算帧率缺口前，先确认瓶颈在哪一侧的账上；worker 侧的数字才是可优化的对象。
**出处**：MAVIS-PERF-V4-AFFINITY-20261123.md 第 37.2 / 37.3 / 37.6 节。
