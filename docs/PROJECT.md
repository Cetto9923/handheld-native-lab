# 项目目标与验收规格

## 用户目标

游戏：《最终幻想：共鸣 / FINAL FANTASY RESONANCE》。用户希望摆脱现有模拟器的卡顿，在安柏尼克 RG477M 本地原生游玩，愿意投入较多 Token，要求多个 Agent 协作、分辨率适配和可持续接力。

现阶段仅建立项目，不宣称原生移植已经可行。不要把“天玑理论性能比第一代 Switch 高”推导成稳定帧率；原作专有平台优化、重编译质量、平台接口、纹理/着色器、驱动和内存都要验证。

## 原生定义

游戏派生代码以 Android NDK 编译为 arm64-v8a 原生代码并真实执行；可以重实现系统和图形 API。允许离线指令/着色器转换和平台兼容层，需公开边界与开销。排除运行时通用 CPU 解释/JIT、模拟器套壳与串流。JNI/Java 的 Android 窗口和界面包装可以存在。

验收证据组合：源模块/地址与实现对应、构建链与 ABI、原生库/符号及执行路径、已加载模块/进程检查和真实行为对照；单凭进程名或“没有 JIT”不足以证明。

## 分辨率规格

- 物理输出以真机面板为准，初始按 1280×960。
- 先核实游戏原生画面比例。若为 16:9，默认在 1280×960 面板中居中显示 1280×720，上下各 120 像素黑边；不拉伸、不裁掉字幕或 UI。
- 候选内部渲染档：1280×720（清晰）、960×540（初始平衡）、854×480（性能，近似 16:9）。这些是待实现的实验档，不是已支持能力。遵守渲染器对齐要求，记录实际 viewport 和 render target。
- 内部渲染、输出合成与 UI 分开适配；若游戏结构不允许 UI 独立高分辨率，记录限制，不伪称实现。
- 先完成固定分辨率基线，再判断是否值得做动态分辨率。动态范围、上下限、变化速度、字幕可读性均需测；不以无记录隐藏降质换通过。
- 正确映射实体手柄、摇杆、确认/取消、菜单、返回、休眠恢复。默认保留原比例，不要求强行填满 4:3。

## 帧率与稳定性：工程初始验收目标，不是结果保证

首个可玩版本目标：在已实现的代表性流程中稳定 30 FPS，清晰度优先选择达到目标的最高固定分辨率。若游戏设计不能正确运行在 30Hz，先研究其逻辑/渲染节奏，不能用降速实现锁帧。

性能区间：真实移动、战斗/高负载、过场各至少连续 5 分钟，分别报告；达不到该场景阶段时标 NOT_RUN。至少三次可重复短测，并做一次 45 分钟混合流程持续运行。固定设备固件、构建 ID、画质、分辨率、屏幕模式、供电、风扇、环境温度与缓存状态。

暖缓存游玩区间初始目标：

| 指标 | 目标 |
|---|---|
| 平均实际游戏帧率 | ≥29 FPS，正确限帧至 30 |
| P95 游戏帧呈现间隔 | ≤35 ms |
| P99 游戏帧呈现间隔 | ≤50 ms |
| 超过 100 ms 的游玩帧间隔 | 每 5 分钟区间不超过 1 次，逐次定位；反复同点卡顿仍 FAIL |
| 持续运行 | 无崩溃、ANR、错图、失控、音频持续破音和存档损坏 |

所有 loading/视频/场景切换边界在测试前定义，同时报告端到端结果与游玩分段，不能事后删去慢帧。冷安装/冷缓存首次进入单独报告，记录着色器首次编译停顿；另测暖缓存，不能用暖缓存掩盖冷启动体验。若源素材视频帧率与游戏不同，分开记录。

指标由原始 frame timestamp 计算，写明时钟、测量点、分位数算法与采集开销。重复呈现同一游戏帧、系统 120Hz 刷新率和 UI overlay 刷新不计作新游戏帧；1% low 如提供则明确计算口径，不能混同 P99。

60 FPS 是后续提升目标：先验证原作帧率设计和游戏速度正确，再决定是否立单独任务。未经真机证据不保证 30/60 FPS，也不宣称“原生必然更快”。无法达到首个目标时保留失败数据，继续按瓶颈优化，不静默放宽标准。

## 阶段出口与完成口径

T00 输入/环境基线 → T01 路线验证与 T03A 宿主/探针构建并行 → T02 游戏真实代码原生样例。T03B 单独进行真机能力验证；T04 的实现可在 T02/T03A 后开始，T04 的真机标题验收还必须通过 T03B。之后依次 T05 可操作场景、T06 分辨率/性能、T07 独立持续 QA。

T02 通过只证明选定代码；T04 通过只证明启动链；T07 通过只证明列出的场景和版本。完整游戏可玩需单独列出实际覆盖流程，未覆盖章节保持未知。没有真机时继续可做的主机工作，Android 性能验收保持 BLOCKED_DEVICE。
