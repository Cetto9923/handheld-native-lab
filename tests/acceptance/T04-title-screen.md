## TS-001 冷启动可达标题画面

- **前置条件**：TSPRE-1…TSPRE-4、DEV-006 PASS（显示模式已固定）
- **步骤**：
  1. 清空 app data（`adb shell pm clear <pkg>`），重新安装 APK。
  2. 冷启动（见 FT-101 的冷启动定义），等待首帧。
  3. 记录从进程创建到标题画面首帧呈现的时间（ms），并抓取首帧截图与视频。
  4. 记录 `logcat` 全程。
- **期望**：在有界的合理时间内出现**本作真实标题画面**（见 TS-002 的判定）。
- **判定口径**：
  - PASS 条件 = 标题画面首帧呈现，且 `logcat` 中无 FATAL EXCEPTION / ANR / SIGSEGV / SIGABRT。
  - **冷启动时长本组不设阈值**（首轮无基线），只记录；阈值由 T07 在有基线后另行确定，且不得由实现者自行放宽。
- **证据产物**：`evidence/t04/cold-start/`（视频、截图、`logcat.txt`、首帧时间戳）
- **状态**：BLOCKED_DEVICE

## TS-002 标题画面身份判定（防硬编码/防视频/防贴图冒充）

- **前置条件**：TS-001 有截图与视频
- **步骤**：
  1. 从运行中的进程取真实标题画面帧（`adb exec-out screencap` 或录屏，**不是**素材文件）。
  2. 与游戏包内可能存在的同名静态资源（若有）做哈希/像素对比，确认来源是实时渲染。
  3. 检查画面里是否存在可交互元素（LOGO 动画、按下开始提示等）随输入变化。
- **期望**：画面是实时渲染且可交互。
- **判定口径**：
  - PASS 条件 = ①截图来自运行中设备；②按下/移动输入后画面**发生可见变化**（有前后帧差）；③帧差非零且非纯 UI 叠加（至少一处非 UI 区域变化，或有明确的动画序列）。
  - 若画面是**预先录制的视频**（例：整段播放与输入无关的 30 fps 视频）⇒ FAIL。
  - 若画面是**硬编码贴图**（无输入响应、无动画）⇒ FAIL。
- **证据产物**：`evidence/t04/title-frame-*.png`、输入前后帧差分析脚本输出
- **状态**：BLOCKED_DEVICE

## TS-003 模块加载清单与顺序

- **前置条件**：TS-001
- **步骤**：
  1. 运行中读取 `/proc/<pid>/maps`，按映射顺序列出所有自有 `.so`。
  2. 记录每个库的路径、大小、SHA-256、加载地址区间。
  3. 与 NSO 模块清单对照：`main`（FFRS-Switch-Shipping.nss）、`rtld`（nnrtld.nss）、`sdk`（NintendoSDK_NVN）、`subsdk0`（NintendoSDK_movie）分别由哪个宿主库承接。
- **期望**：加载清单可解释、无缺失、无意外。
- **判定口径**：PASS 条件 = 全部映射库都能归类到「宿主自有 / 平台兼容层 / 系统库」，且游戏派生代码来自 `main`；**没有**整个游戏包被整体映射。
- **证据产物**：`evidence/t04/proc-maps.txt`、`module-load-map.json`
- **状态**：BLOCKED_DEVICE

## TS-004 原生执行链证据（真实执行，不是模拟）

- **前置条件**：TS-001、NS-006 PASS
- **步骤**：
  1. 在标题画面路径上捕获至少一个**已知游戏函数**（来自 `main`，UE 5.6.1 基线）的实际执行证据（例如计数器/断点/指令级 trace，证明它在 ARM64 上跑的是重编译后的 AArch64 代码）。
  2. 记录该函数在本实现中的符号与地址。
  3. 记录证据采集方式（perfetto / gdb / 插桩 / 计数器）。
- **期望**：能证明游戏代码路径确实在 ARM64 上原生执行。
- **判定口径**：PASS 条件 = 存在**可核验**的执行证据，且该证据指向游戏函数而非宿主壳函数。
**单凭"进程名"或"没有 JIT"不算通过**（PROJECT.md 明确）。
- **证据产物**：`evidence/t04/native-exec-chain/`
- **状态**：BLOCKED_DEVICE

## TS-005 标题画面输入响应

- **前置条件**：TS-002 PASS、DEV-007 PASS
- **步骤**：
  1. 用手柄按下确认键 → 记录画面变化与日志。
  2. 按下取消/返回 → 记录反应。
  3. 摇杆轻微移动 → 记录是否有 UI 焦点变化。
- **期望**：输入被正确映射（确认/取消/菜单/返回）。
- **判定口径**：PASS 条件 = 每个被测按键都产生了**可区分的、预期的**画面或状态变化；摇杆有 deadzone 且焦点移动平滑。
- **证据产物**：`evidence/t04/input-response/`（按键前/后截图对）
- **状态**：BLOCKED_DEVICE

## TS-007 标题画面分辨率与宽高比呈现

- **前置条件**：TS-001 PASS、DEV-006 PASS
- **步骤**：
  1. 在 1280×960 面板上截取标题画面。
  2. 测量 3D 内容区域的实际像素包围盒与黑边宽度。
  3. 记录内部渲染分辨率、输出合成分辨率、UI 分辨率三者实际取值。
- **期望**：16:9 内容居中，上下各 120 px 黑边；不拉伸、不裁掉字幕或 UI。
- **判定口径**：
  - PASS 条件 = 内容区域宽 = 1280、高 = 720；上下黑边各 = (960-720)/2 = 120 px（允许 ±2 px）；
    内容区域水平居中（左右黑边相等，|差| ≤ 2 px）；
    内容宽高比 = 1280/720 = 1.7778 ± 0.002（证明未拉伸）；
    标题 UI 元素完整落在内容区域内（无裁切）。
  - 若黑边不是 120 px 或内容被拉伸/裁切 ⇒ FAIL。
- **证据产物**：`evidence/t04/title-frame.png`、`letterbox-measurement.json`
- **状态**：BLOCKED_DEVICE
